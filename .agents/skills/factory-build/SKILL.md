# PokeFactory2 Build

这是一个**长时程委派工作流**。orchestrator 制定多阶段计划、派发给队友、监督执行。**orchestrator 不亲自实现**——只有几行的局部修改才算自助。

核心职责：
- **理解**：从代码、规则文档、真实运行重建当前现实
- **架构**：在执行前设计多阶段计划
- **监督**：委派、跟踪、通过队友纠偏

---

## Phase 1：计划

把目标澄清到具体可执行。**未对齐前不进入执行。**

1. 用最多 3 个并行只读子 Agent 侦察三个面：
   - **当前代码库** — 既有文件、模式、spec、实现状态
   - **`docs/` 规则面** — 规则定稿、需求矩阵、任务目录现状
   - **参考实现面** — `reference/pokeemerald-expansion`、`output/rogue-expansion-reference`
2. 涉及玩法机制时，**先派 `designer` 补齐设计层缺口**并更新规则定稿。
   - 规则一变，就对着用户原话做一次保真检查（用 VLM 或人工比对）：列出规则文档漏掉/弱化/矛盾的要求，逐条引用双方原话。
   - 任何偏离都要打回 designer。
3. 拆成**宏阶段**。每个阶段要有：
   - 完成时项目到达的状态
   - 该状态如何被检验
   - 哪些前置阶段必须先完成
   - 阶段就绪后可同时启动的任务
4. **阶段内挑可并行的独立任务**：
   - 单一有界交付物 + 清晰归属
   - 清晰验收条件
   - 对同阶段其它任务无隐藏依赖
   - 若兄弟任务共享不稳定的核心接口/状态模型/核心文件 → 合并成一个任务
   - **同一个战斗控制器禁止并发**
5. 填 `.agents/goal.md`：`## Task Breakdown`（阶段计划）与 `## Done When`（可勾选的目标结果，不是「游戏能跑」）。永不编辑 `## User Input`。
6. **把文件给用户看，等明确批准后再执行。** 用户可以要求合并/拆分/删减任务——任务范围是用户的决定。
7. 本阶段**不要**创建 reviewer。

---

## Phase 2：执行

1. 创建 reviewer 作为常驻成员（全程一个，**不**每阶段新建）。告诉它目标是什么，并要求它：
   1. 立即创建 `.agents/review-lock.json` 为 `{"locked": true}`，目标达成前不释放
   2. 从规则定稿/需求矩阵/交接文档理解目标
   3. 了解当前代码库后等待最终审查通知
2. 每个阶段：
   - 建任务目录（`docs/tasks/<name>/`）并初始化 `prd.md`
   - **为无依赖的任务并行派发 programmer**
   - 按 `AGENTS.md` 的流水线走：architect → programmer → auditor → player
   - 阶段完成后更新 `.agents/goal.md` 的进度勾选
3. 全部阶段完成后，通知 reviewer 请求最终审查（用 `AGENTS.md` §6 的交付格式）。
4. 等裁决。通过则释放锁；驳回则处理反馈并重新请求审查（**reviewer 每次都要重跑完整清单**，不是只看新修复）。

---

## 规则

- **永不亲自实现**，除非是几行的琐碎修改。
- **reviewer 常驻**：整个 session 只创建一次；所有审查请求发给同一实例；**不做分阶段审查**。
- `review-lock.json` 归 reviewer 所有，不归 orchestrator。
- 阶段保持宏观。详细实现归 architect / programmer。
- **最大化并行**：无依赖的 programmer 同时派。
- 用明确的 blocked-by 声明依赖。无阻塞的任务立即启动。

## 本项目的并行禁区

- 战斗控制器（`useBattleController.ts`）同一时间只允许一个任务改动。
- 存档结构（`saveManager.ts`）改动要串行，避免版本号冲突。
- 主工作区的未跟踪试玩证据不可批量清理，也不可 `git add .`。
