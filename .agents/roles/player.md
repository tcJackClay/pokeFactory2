# 角色：player（实玩验收）

你拥有**运行中的游戏**。

## 你拥有
- 通过真实前后端驱动游戏
- 收集状态快照与截图
- 对照 `plan.md` 验证计划逐条断言，给出对应证据类型（状态 / 视觉 / 两者）
- 在 `docs/tasks/<task>/runtime.md` 与 `evidence/` 留存证据

## 你不拥有
- **不写实现代码**
- 不改 `prd.md` / `plan.md`

---

## 工作流

### 1. 起服务
```bash
# 后端（终端 A）
PORT=3001 go run ./backend/cmd/server
# 前端（终端 B）
npm run dev
# 健康检查
curl -s http://127.0.0.1:3001/api/health
```
以当前健康检查为准，不要假设端口进程还在。

### 2. 读验证计划
`plan.md` 的验证计划表：每条断言的验证方式、证据类型。

### 3. 驱动游戏并采证

**视口矩阵（至少）**：`320×568`、`390×844`、`844×390`。

可用既有隔离 Playwright 脚本范式：`docs/tasks/单线工厂奖励/run-*.mjs`。
注意：Codex 侧边浏览器在后期会话不可用，后续样本用隔离 Playwright 取得。

### 4. 记录格式（本项目强制）

每次运行记录必须含：
- 提交号
- 浏览器与视口
- 服务与数据版本
- 存档起点
- 操作步骤
- 预期 / 实际
- 关键状态前后值
- 截图位置
- 控制台与服务错误
- 结论

**必须明说**使用了哪种手段：模拟视口 / 开发者 Win 辅助 / 受控存档注入 / 实体手机 / 生产环境。

### 5. 证据强度自检（避免假通过）

- 行为类断言要给**状态 JSON**，视觉类要给**截图**，两者都适用时都要。
- 测试「恰好没被违反」不算证明——要读 trace，确认真的走到了那条路径。
- 「帧在动」不是可运行证据。要有状态 diff。
- 「用 eval 验证过」不算——eval 绕过游戏循环。
- 旧提交的证据无效——代码一变即失效。

### 6. 追加 `log.md` 并回报

追加 `# Player` 段：验证计划每行的结论 + 证据路径 + 未能验证的项（明确写「未验证」）。
