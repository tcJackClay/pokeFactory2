# 四张不同且可领取奖励卡的候选覆盖分析

基线为 `origin/dev` 的 `50fece7`。用户已批准的持有物仅有 `scope_lens`、`quick_claw`、`kings_rock`、`choice_band`、`focus_band`，并要求三名队员的本局装备互不重复。TM 来源为固定 Rogue expansion 的 50 项及物种普通 profile，但上游“可学”还须经过本项目物种/形态映射、当前队伍已学招式排除、资料可用与战斗效果准入。参考表有固定租借原配持有物，**没有本项目四卡奖励规则**；表中出现不构成玩家批准发卡。

## 必要且可计算的条件

设 `H` 为已获准、可对当前队伍任一成员装备且效果合格的**不同**持有物 ID 集合；`E` 为三人下一战返还基准的非空装备 ID 集合（用户要求 `|E| ≤ 3`）；`T` 为三人至少一人按 Rogue 普通 profile 可学、当前未掌握、映射和战斗效果均通过准入的**不同** TM ID 联集；`O` 为另行获准且真正可领取的其他战斗道具 ID 集合。只有在

`|H \ E| + |T| + |O| ≥ 4`

时，才有四张不同且可领取的候选；生成器还必须从这个已验证集合不放回选取并冻结结果。若产品规定每类卡的固定数量，另须分别满足各类下限，例如 2 ITEM + 2 TM 要求 `|H \ E| + |O| ≥ 2` 且 `|T| ≥ 2`；仅满足总数不够。当前四卡 ITEM/TM 比例、其他道具与候选不足处理尚未定稿，不可用重复卡、不可学 TM、旧奖池或空卡填充。

持有物候选必须按**本局装备返还基准**计算，不能按本场可能被消耗/拍落的 `factoryHeldItemId` 计算。对任一 `h ∈ H \ E`，若它不受物种限制，三人任意一人均可替换旧装备且保持互不重复，故它贡献一张可领取卡；`h ∈ E` 则无合法目标，给原持有人“原物再装备”也不算可领取。换入敌方成员后应先核验整队装备唯一性，再重算候选，不能擅自丢掉敌方原配道具。主线目前只有 `factoryOriginalHeldItemId` 与当前持有物，尚无奖励装备的可变返还字段；此处公式是目标规则的口径，不是现有生成器能力。

五件已批准持有物的最坏合法状态是三人分别装备其中三件，此时 `|H \ E| = 5 − 3 = 2`，所以**必须另有至少两张合格 TM 或其他已批准卡**才能凑四张。现有固定 TM 提取证明上游普通 profile 有 16 份零交集，项目基础物种在尚未扣除当前已学招式与战斗效果时也有 16 种零 TM、40 种少于四；这不能直接证明实际会抽出“三人零 TM”队伍，但足以否定“每个成员都贡献 TM”的假设。当前主线尚未有经完整战斗效果和奖励端到端验收的可发 TM allowlist，不能拿原始 50 项为四卡兜底。

若产品要**独立于 TM 组合**地保证四张，同时只用无物种限制的不同持有物卡、三人装备唯一，则需要 `|H| ≥ 7`，因为最坏三件已占用，仍剩四件；这是数量下界，不等于下面候选已获批准。若使用其他道具或保证每队 `|T| ≥ 2`，可维持五件持有物，但必须用九代全部可达三人队、换怪后队伍、已学招式与当前 TM 准入名单实测证明这个下界；原始 profile 计数无法替代证明。增加第六件只能把最坏缺口缩至一张，仍不能无条件保证。

## 可供设计决定的参考表补充候选

下表仅为需用户确认的**提案**。均确实出现在 `reference/pokeemerald-expansion/src/data/battle_frontier/battle_frontier_mons.h` 的租借原配表；本地表中 `ITEM_BRIGHT_POWDER` 80 处、`ITEM_WHITE_HERB` 25 处、`ITEM_MENTAL_HERB` 4 处。这些出现次数不是本游戏发卡权重，也不能推出物品在任意队伍中有用。

| 候选 | 已有代码效果 | 准入缺口 |
| --- | --- | --- |
| `bright_powder` 光粉 | `itemEffects.ts` 定义对手命中倍率 0.9，`resolveAccuracy.ts` 读取防守方当前持有物。 | 设计文档此前明确建议暂不放入最小池，因为增大随机闪避；若重新考虑，先批准体验取舍，再做固定随机命中边界、双方装备与逐战返还的结果测试。 |
| `white_herb` 白色香草 | `useBattleController.ts` 在能力等级降低后尝试恢复并消耗；已有隔离手机浏览器“过热后消耗、下一战返还”局部证据。 | 须确认战斗中能力恢复类持有物符合“首版无回复类奖励”的边界；检查所有降能力入口、领取换装和替换旧物、被消耗后下一战按新装备返还。现有浏览器样本是注入道具，不是奖励领取。 |
| `mental_herb` 心灵香草 | `itemEffects.ts` 列出挑衅、再来一次、无理取闹、定身法等心智状态；`useBattleController.ts` 的 `tryConsumeMentalHerb` 可清理并消耗。 | 同样须由设计确认类别；以真实妨碍招式测试各支持状态的触发时点、双方目标、一次性消耗及下一战返还。仅有元数据与调用入口不能视为效果已验收。 |

如果批准其中两件且都能对任意队员装备，经效果验收后持有物池达到七件，数量上可覆盖 TM 联集为零的最坏情况；实际能否发四张仍依赖物品资格、装备唯一性、奖励检查点及加载成功。若这三件都不符合体验方向，就需要别的已批准、无物种限制的卡源或正式改变“四张不同且可领取”的产品规则，不能让程序自行补物品。

## 可重复验证

从冻结的 Rogue TM 映射和已验收 allowlist 计算每个可达三人队的 `T`，扣除各自已掌握四招；枚举三人的合法装备位和第 3/6 胜换怪结果，按上式输出 `0/1/2/3/≥4` 分布与最小反例。测试同时断言持有物 ID 不重复、候选均有合法队员、领取再次校验、刷新候选不变、失败留在奖励节点而不推进。随后在 390×844、844×390 浏览器完成第 3 与第 6 胜的真实四卡展示、装备替换、下一战返还及刷新；随机边界用确定性夹具单独补证。当前主线尚未完成这些流程，静态数量推导不能宣称已经达到发布状态。
