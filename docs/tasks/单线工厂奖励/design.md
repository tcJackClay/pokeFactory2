# 单线工厂奖励设计

依据用户最新决定、《宝可梦对战工厂_项目设计框架_v1.md》§4.2–4.5、《docs/公开版规则定稿.md》和当前代码。旧 `docs/tasks/Rogue模式/design-options.md` 是**未批准的双模式草案**，只用于识别可复用页面与风险；其中原先第 4/7 战前的代码触发点不能代替现行“每组第 3/6 胜后”规则，旧提案的商品与价格也未获批。参考 Battle Factory 的七战、换怪及 BP 见《docs/对战工厂原型核对.md》；奖励卡与补给券属于本项目扩展。

## 已定玩家行为

| 项目 | 当前决定 | 来源边界 |
| --- | --- | --- |
| 主线 | 首版只有一条工厂挑战主线；不提供 Classic/Rogue 两种模式选择。 | 用户最新决定覆盖早前双模式设想，也覆盖早前“Classic 胜后无奖励卡”。 |
| 奖励节点与顺序 | **每组**第 **3、6 场胜利后**各出现一次四选一奖励卡；先完成可选换怪或跳过，再进入卡片页，领取一张。卡片加载失败时留在该节点并提供重试，不跳到下一战。 | 用户本轮定稿；当前第 4/7 战前旧配置在时间上可对应前一胜后，但实现必须以胜后一次性节点为准。 |
| 奖励内容 | 首版卡片只开放**战斗相关道具**与**招式机**，其中战斗相关道具包括可选队员装备的持有物；不开放回复类道具、新宝可梦、进化或队伍扩容。工厂战斗结束后队伍状态自动恢复，卡片无须承担回复功能。 | 用户已定类别和持有物装备行为；具体道具及招式机名单尚未批准，不能直接开放现有 `rewardPools.ts` 全部 ITEM。 |
| 持有物领取 | 选中持有物卡后选择当前租借队员装备；若该队员已有持有物，显示替换并由玩家确认。旧持有物被替换，不进入背包；新持有物成为该成员本次挑战以后每场战斗开战前返还的持有物。 | 用户最新定稿。参考工厂固定租借队本身有持有物，但没有本项目的奖励卡装备流程。新持有物不是基地永久装备，也不是背包物品。 |
| 本局补给券 | 每场胜利获得 **1 券**；跨七战组保留，直到整次挑战结束。它是局内资源，与持久基地 BP 分开。首版**不重抽**奖励卡。 | 用户本轮定稿获得数值、跨组生命周期与禁用重抽；商品、价格、限购及兑换入口仍待定。旧“每件 2 券”和 BP 重抽价均未获批。 |
| 基地 BP | 七战整组获胜后按已定工厂单打表发放；第 1、2 组各 3 BP，之后按表；实际击败工厂首领额外 10，败退 0，余额上限 9999。 | 用户此前明确决定，最新奖励卡决定未覆盖这条。补给券不能冒充 BP，旧重抽 `50 + 50n` 扣 BP 不能直接作为新规则。 |
| 租借与换怪 | 工厂仍六选三，每组第 1–6 胜后可从刚击败的敌队换一只或跳过，第 7 胜后不换。第 3、6 胜时先处理换怪，再选奖励卡。 | 参考实现提供换怪骨架；奖励卡顺序由用户本轮定稿。 |

## 当前实现与复用范围

- `src/features/game/components/game-view/RewardScreen.tsx`、`hooks/useRewardFlow.ts` 已有四卡界面、选择/重抽、ITEM/POKEMON/TM/EVOLUTION 等处理，可复用交互骨架。现有 `grantItemReward` 把 ITEM 全部放入背包，**没有持有物装备/替换流程**。首版只允许 ITEM 与 TM；POKEMON、EVOLUTION 和队伍容量许可必须被排除。ITEM 子池与 TM 候选仍待定，不能把全部旧奖励池直接开放。
- `src/features/game/utils/restoreFactoryParty.ts` 的 `prepareFactoryPartyForBattle` 从 `factoryOriginalHeldItemId` 给成员返还持有物。租借初始化在 `useFactoryFlow.ts` 同时写入该原配字段与当前字段。奖励装备时必须将新物品写为该成员本次挑战的新返还基准，并同步当前装备；旧值不得转入 `inventory`。战斗中被消耗或拍落的当前字段仍可暂时为空，下一战准备时返还新基准。换怪带来的新成员按自身持有物基准处理。
- `src/features/game/config/factoryRewards.ts` 仍存 `preBattleRewardBattlesInSet: [4, 7]` 和四选一配置；旧时点在代码上可对应第 3/6 胜之后、下一战之前，但主流程当前仍跳过奖励卡，且该代码并未保证胜后事件只触发一次。实现应以用户的胜后节点定义为准。
- `src/features/game/hooks/usePokeFactoryGame.ts` 的组末摘要仍写 `mode: 'CLASSIC'`；对单线产品，这是旧内部标签，不应在玩家界面或验收中造成“两模式”误解。`src/services/saveManager.ts` 的恢复快照目前没有 `REWARD` 阶段及奖励选择状态，必须补上后才能在卡片页刷新恢复。
- `RewardScreen.tsx` 和 `useRewardFlow.ts` 的旧重抽公式 `50 + rerollCount × 50` 直接扣 `spendWallet`（基地 BP）；首版重抽须禁用，不能扣 BP 或券。`usePokeFactoryGame.ts` 的 `shopItems` 未接可操作商店；现有 `rewardPools.ts` 只给物品候选，不定义券价或兑换流程。
- `docs/tasks/组末BP结算/runtime.md` 与 `docs/tasks/跨组首领结算/runtime.md` 验的是**无奖励卡旧路径**的组末 BP；这份证据可保留为 BP 基线，不能替代第 3/6 胜新路径的实玩。

## 最小卡池提案，尚未批准

以下是为打通四选一提出的候选白名单，不是已定奖励表、概率或商品价。参考源码 `reference/pokeemerald-expansion/src/data/battle_frontier/battle_frontier_mons.h` 列出的是**固定租借宝可梦的原配持有物与招式**，不能据此推断原作存在奖励卡。当前战斗效果以本项目代码为准。

| 类别 | 候选 ID | 可验证的现有效果与来源 | 建议理由及限制 |
| --- | --- | --- | --- |
| 持有物 | `scope_lens`（焦点镜） | 参考租借表含 `ITEM_SCOPE_LENS`；本项目 `itemEffects.ts` 提高 1 级会心率，`resolveDamage.ts` 读取持有物会心修正。 | 效果可见且不涉及回复，作为基础攻击向候选。 |
| 持有物 | `quick_claw`（先制之爪） | 参考租借表含 `ITEM_QUICK_CLAW`；本项目 `itemEffects.ts` 定义 0.2 先制触发率，`useBattleController.ts` 决定行动顺序时读取。 | 提供速度向选择，需在战斗日志/视觉上说明触发。 |
| 持有物 | `kings_rock`（王者之证） | 参考租借表含 `ITEM_KINGS_ROCK`；本项目 `itemEffects.ts` 定义 10% 畏缩，`useBattleController.ts` 命中处理读取。 | 提供控制向选择；具体哪些攻击可触发应以现有战斗引擎验收。 |
| 持有物 | `choice_band`（讲究头带） | 参考租借表含 `ITEM_CHOICE_BAND`；本项目 `itemEffects.ts` 定义物理伤害 1.5 倍，`resolveDamage.ts` 应用倍率，`useBattleController.ts` 与 `evaluateAiMove.ts` 处理锁招。 | 通用攻击向候选；需验证换人与战斗结束解除临时锁招，不把锁招状态当装备长期效果。 |
| 持有物 | `focus_band`（气势头带） | 参考租借表含 `ITEM_FOCUS_BAND`；本项目 `itemEffects.ts` 定义 10% 致命伤保留 1 HP，`useBattleController.ts` 触发后清除本战当前持有物。 | 通用防守向候选；当前持有物在战斗中可消耗，下一战依新返还基准恢复，须单独验收。 |
| 战斗消耗道具 | `battle_atk`（力量强化）、`battle_def`（防御强化） | `uiAppConstants.ts` 标记 `isBattleItem`；`useBattleController.ts` 已有使用与消耗入口。 | 可组成纯战斗用途 ITEM 子池；是否与持有物同时入首版卡池仍需用户确认。 |
| 招式机候选 | `protect`（守住）、`brick-break`（劈瓦）、`aerial-ace`（燕返） | 参考租借表出现 `MOVE_PROTECT`、`MOVE_BRICK_BREAK`、`MOVE_AERIAL_ACE`；本项目 `moveEffectTable.ts` 有守住、劈瓦的专用效果，其余由通用招式流程处理。 | 仅作为三个具体起始候选；出卡时须确认当前队伍至少一名队员在选定数据版本能通过**招式机方式**学习、尚未掌握，且招式效果在游戏中能正常结算。参考租借表出现招式不等于可用招式机资格。 |

建议暂不放入 `leftovers`、`shell_bell`、`sitrus_berry` 等回复持有物，遵守“无回复类奖励”；`bright_powder` 改变命中随机性，先不入最小池；`loaded_dice` 虽有现成效果，但不是上述参考租借表的原配项。特定物种装备如 `thick_club` 只对少数队员有效，也不适合作为通用卡。现有 `rewardPools.ts` 的 `potion`、`heal`、特殊触发物和 `team_capacity_permit` 不能直接带入。

每张持有物卡展示前须至少有一名当前租借队员可将其装备为**不同于该队员返还基准**的新持有物；玩家选卡后只允许选择这些队员。若同名持有物已装备在一位队员身上，不因此排除给其他队员装备同名物，但不得出现全队都没有有效目标的卡。参考原作对同队重复持有物的限制若要沿用，需另行确认；当前用户只定了替换去向与返还行为。由于队伍有三名队员，五件持有物本身不能保证在所有队伍状态下凑满四种有效卡，仍需 ITEM 消耗品或合格 TM 补位，并在生成时验证四张卡各自能领取。

现有 `getLearnableMoves` 只从宝可梦可学招式中排除已掌握招式，**没有按机器学习方式或版本筛选**；`buildTmReward` 随机选一招且旧生成器至多放一张 TM。若采用本提案，应先建立可核查的招式机资格来源，再按当前租借队动态筛选。提议四张卡尽量不同；若没有合格 TM，用不重复的合格 ITEM 补足四张并保留四选一。此补位策略和 ITEM/TM 比例仍待批准，不得把“可学招式”直接标作招式机。

## 仍待定的最少必要决策

| 优先级 | 需要用户定夺 | 为什么不能由代码默认值代替 |
| --- | --- | --- |
| 1 · 卡片具体池 | 是否采用上方五件通用持有物、两件战斗消耗道具和三招的起始名单；招式机资格采用哪个版本的数据；四卡中 ITEM/TM 比例及 TM 不足时是否用 ITEM 补位？同队同名持有物是否允许？ | 持有物装备/替换/本局返还已定；**具体 ID、出卡比例、同名规则和招式机数据源未定**。现有 TM 生成器未筛机器学习方式，ITEM 旧池含越界物品。 |
| 2 · 补给券消费 | 哪些商品可兑换、各需多少券、每次或每局限购多少、兑换入口何时开放？ | 每胜 +1 与跨组保留已定，但没有商品表和价格就不能形成可试玩消费闭环；旧提案的每件 2 券未获批。 |

这两项得到决定即可编写包含补给消费的完整实现任务；奖励节点、持有物装备和券获得已有足够规则可先实施。捕捉、特殊机制扩展及随机事件若要改变主线，另走规则定稿；基地商店商品继续单独待决。无需再询问是否双模式、后续组出卡节点、换怪先后、持有物替换去向与返还、每胜券数、是否重抽或是否发组末 BP，这些已有最新决定。

## 验收路径

新档进入唯一工厂主线，六选三后完成首组：第 1、2、4、5 胜只有常规赛后路径，第 3、6 胜各恰好出现一次四选一且只领取一张；在这两场先换怪或跳过，再选卡；卡加载失败留在节点并可重试，不推进战次。选中持有物卡后能选当前租借队员，明确显示原持有物并确认替换；旧物不进背包，新物成为此成员后续每战返还基准。用可消耗持有物或拍落场景验证：结果页保留战斗结束时的当前状态，下一战开战前返还奖励装备；换怪、刷新和同版导入后仍按所选成员与新基准返还。第 7 胜不出现换怪/卡片，组末 BP 依原型表入基地钱包，已获补给券跨组保留。第二组再次在组内第 3、6 胜出卡；每胜券余额只加 1。任一奖励节点刷新、重开和同版导入应保留已展示候选、已领卡、券余额、队伍和战次，不能重新抽取或重复领取。败退不增加 BP；整次挑战结束后局内券清除，基地已有 BP 保留。重抽按钮不出现或禁用，绝不调用旧 BP 扣费。商品与价格待定后补兑换验收；模拟手机浏览器和实体手机分别记录。
