# Rogue 持有物奖励池实施与验收计划

本计划以用户最新方向为前提：扩展持有物池，参照 Pokabbie/pokeemerald-rogue `expansion` 的独立 Held Items 商店，同时保留每组第 3、6 胜后的四张不同且可领取卡。固定参考提交为 `a6adfcf18d7eaf99c2803e4b0bc04eca7af2f014`；筛选链、分层目录和源码行号见 `rogue-held-item-shop-reference.md`。商店按启用、口袋、价格、运行难度、种子和解锁动态筛选；此处只借其**持有物分类和战斗效果**，不复制价格、库存概率或解锁进度。

## 实施边界与候选

首批基础池是已确认的 `scope_lens`、`quick_claw`、`kings_rock`、`choice_band`、`focus_band`，再纳入 Rogue 商店且本项目已有战斗入口的 `heavy_duty_boots`、`loaded_dice`。这七件都可给任意租借队员装备，三人本局装备互不重复时，最坏仍有 `7−3=4` 个不同、可装备 ID，因此**数量上**不依赖 TM 即可提供四卡。按用户已授权的扩池方向先实现新增两件，效果、装备、返还和手机验收通过后才标记可发；只有元数据不等于可发卡。`loaded_dice` 对没有合格连续攻击招式的队伍可能暂时无收益；“可装备/可领取”和“当前队伍能触发效果”应在卡面区分，不可为凑数谎称当局一定有效。若设计要求四张都能在当前队伍触发效果，七件的数量下界不再足够，需要另定额外通用池或队伍级覆盖规则。

第二层可以加入本项目 `itemEffects.ts:166–180` 已列的 15 件属性强化道具，例如 `silk_scarf`、`charcoal`、`mystic_water`、`magnet` 等。只在当前三人至少有一招已装备、可造成伤害且属性匹配时，把相应卡作为“当前队伍适用”候选；按招式实际攻击属性判定，排除纯变化招式、已失去的技能或当前成员都不匹配的物品。它们扩大玩家可选空间，但基础七件始终保留为四卡数量保底。Rogue 固定配置 `include/config/item.h:15` 与 `src/data/items.h:17–21` 将普通属性强化设为 **1.2 倍**；本项目 `itemEffects.ts:166–180` 为 **1.1 倍**，必须先修正并以伤害结果测试证明，再开放这一层。物种限定物品仅对匹配物种/形态入池，不计入通用保底。回复类、树果、形态石、尚无战斗效果的商店物品不因出现在 Rogue 商店就自动开放。

气势头带另有已存在的原型差异：本项目 `useBattleController.ts:2126–2140` 成功挺住时调用 `consumeHeldItem`；Rogue `src/battle_script_commands.c:2185–2189` 只设置挺住标志，`data/battle_scripts_1.s:10241–10248` 只在目标持有 **Focus Sash（气势披带）** 时移除物品，Focus Band（气势头带）不消耗。若以 Rogue 战斗效果为准，须把气势头带改为每次合格致命伤可独立判定且本场不消耗，并更新展示、存档与测试；否则应在设计中明确标为本项目扩展规则，不能宣称已对齐 Rogue。此差异应在首批发卡前解决。

## 最短实施顺序

1. 固定源清单：从 Rogue 运行时 `POCKET_HELD_ITEMS` 语义建立显式 `ITEM_* → 项目 item ID → effectId → 是否通用 → 是否已验收` 表；基础七件先锁定。检查 `heavy_duty_boots`、`loaded_dice` 的源 ID、项目元数据和对应入场/连续攻击调用，不使用原始 `items.h` 的 `.pocket` 当最终分类，也不把树果、Rare Held Items 的 `POCKET_STONES` 混入。新增候选必须逐项过效果准入后才加入发布 allowlist。
2. 先完成首批效果修正和结果测试：厚底靴对隐形岩、毒菱的正确免疫与毒属性吸收顺序；连续攻击道具在 2–5 次连续招式上的次数分布/确定性边界与无此招式时的真实提示；气势头带的消费差异按已定规则收敛；已批准五件保留原有会心、先制、畏缩、物攻锁招和挺住效果。随后修正 15 类属性强化的 1.2 倍及适用招式判定，再逐件开放，不能把 15 个配置字段一次性当作 15 项验收通过。
3. 奖励生成在第 3/6 胜换怪结束后的**最终三人队**上枚举候选：比较每人的本局装备返还基准，而非本场被消耗/拍落后的 `factoryHeldItemId`；已在三人任一装备位的 ID 不出卡。对每张卡至少给出一个合法装备对象；同名 ID 只出现一次。先证明合格候选数 ≥4，再按冻结的随机源不放回选四张。可执行的最短随机方案是对已验收、不同 ID 的合格卡等权抽样，ITEM/TM 不强制固定配比；这是一项待设计确认的建议，权重应置于独立配置，不能沿用 `useRewardFlow.ts` 旧 `FREE_REWARD_TYPE_WEIGHTS`、十次重抽或旧 POKEMON/EVOLUTION 池。若设计随后指定类别比例或稀有度，再调整配置并重新验证四卡覆盖；不得由旧代码默认值暗定。如果计算或资料加载失败，保留奖励节点并给可重试反馈，不推进战次、不少给或重复卡。
4. 领取时玩家选择队员并确认替换，旧物直接移除且不进背包；新物写入本次挑战后续战斗的可变装备返还基准，并立即显示为当前装备。被消耗/拍落的旧装备不得在奖励页自动复活，新装备在下一战开战前按最新装备位返还。领取、候选和队员选择要落在同一 `READY → CLAIMED` 原子检查点，刷新或双击不得重复领取。换怪时若敌方成员装备与余下两人冲突，保持可选择其他组合或跳过；不能悄悄丢弃其道具。`saveManager.ts`、`restoreFactoryParty.ts` 与奖励分支要采用同一字段/校验口径；当前主线仍仅有 `factoryOriginalHeldItemId` 和当前物品，奖励装备事务尚未合入。
5. 九世代物种池单选不自动限制道具世代：Rogue `ItemToGen` 会限制个别物品（如王者之证），本项目设置目前只控制物种来源。若要另引入道具世代解锁，需明确产品规则，并重新证明每个世代候选至少四张；当前计划保留基础七件跨九池可用。

## 可测验收

| 场景 | 结果断言 |
| --- | --- |
| 三人已装备基础七件中的任意三件，TM 候选为零 | 基础池至少剩四个不同可装备 ID；四卡恰好四张、无同名、每张至少一个合法队员；抽样种子改变选择但不改变资格。 |
| 初租借、胜后换怪、装备奖励及战中消耗/拍落 | 任一时点本局装备基准三人不重复；候选依基准过滤；替换旧物不入背包；新装备本页即时可见，下一战返还同一物品。 |
| 厚底靴、连续攻击道具、气势头带 | 各有双方战斗结果断言；厚底靴不跳过毒属性吸收；连续攻击道具只有合格 2–5 次招式才改次数；气势头带依最终规则可重复触发或按明确扩展规则消耗。 |
| 属性强化层 | 对匹配伤害招式是 1.2 倍、不匹配和变化招式不增伤；十五种逐件映射及至少各类边界测试通过才标可发；没有匹配招式时不伪称当前适用。 |
| 奖励事务、失败与刷新 | 第 3/6 胜先换怪再生成；固定四卡刷新不变、双击只领取一次、失败留节点重试；同版保存恢复后装备、候选、领取状态与下一战返还一致。 |

静态门禁使用仓库现有 TypeScript、战斗测试、奖励检查点和构建测试；不以只读的源表数量或 metadata 存在代替伤害/行动结果。手机浏览器在 390×844、320×568、844×390 真实通过第 3 与第 6 胜：查看四卡、选队员、确认替换、刷新、进入下一战并实际触发新增持有物效果，记录装备位、HP/PP/日志、请求与截图。确定性测试夹具负责覆盖极端三件占用、TM 零候选及概率效果；浏览器自然长局负责证明玩家流程可达。实体手机触控另验。公开发布前仍需单独完成来源/素材权利审查。
