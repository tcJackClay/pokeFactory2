# 九世代租借池加载性能计划

## 已知证据与待测问题

- player 的稳定第 1 代样本：点击开始挑战至六卡约 5.95 秒，至首战约 13.92 秒。后一数字是否包含玩家挑选三只、确认和训练家入场等待，现有记录无法拆分；不能直接把约 8 秒差额归因于敌队资料。第 2 代样本受热更新干扰，不纳入基线。
- `usePokeFactoryGame.ts` 的 BOOT 异步调用 `prefetchRentals()`，并不等待预取完成才让玩家进入基地。`startGame()` 复用同键预取或等待进行中的请求；成功显示 `FACTORY_SELECT` 后才调用 `prefetchEnemy(1, { factoryPool: rentals, playerPool: [] })`。因此从点击起计时会混入 BOOT 阶段已完成的工作，必须另报启动至预取完成的时间。
- `useFactoryFlow.ts` 的 `generateRentalDraft()` 先载入同源 `/api/data/factory-species-index`，`buildFactoryPool()` 按六个名额逐次筛选并逐只调用 `getProcessedPokemon()`。索引命中时候选元数据不需额外物种请求；索引缺项时会走宝可梦、物种、进化资料回退。`getProcessedPokemon()` 读取宝可梦与物种资料，`hydratePokemonDetails()` 逐个等待特性资料；当前六卡路径启用完整资料，四个选定招式的请求已由 `Promise.all` 并发，不能再把它写成“招式逐条串行”。六只完整成员之间仍串行，候选尝试最多 `6×25` 次。
- 六卡出来后敌队预取开始；训练家模板与本地 Frontier set 仅用于适用的同世代筛选，若不足则按项目规则回退到该世代随机池。`confirmRentals()` 调用 `spawnEnemy()`，其缓存键匹配时复用预取，否则等待同键进行中任务或重新生成。`startBattleTransition()` 会先把状态设为 `BATTLE`，所以“进入战斗画面”不代表敌队准备完或可点击出招。
- `pokeApiEndpoint.ts` 默认 JSON 地址是同源 `/api/pokeapi/*`，有单请求超时、资源总期限和有限重试；`factorySpeciesIndex.ts` 也有 4 秒超时，租借预取有 30 秒上限及失败提示。`pokeApi.ts` 保留宝可梦、物种、特性和招式内存缓存；端点层合并同路径进行中的 JSON 请求。Go 内容服务先读版本库，再读运行缓存，允许回源时才访问 PokeAPI，响应 `X-Content-Store` 可区分 `VERSION`、`RUNTIME`、`UPSTREAM`。浏览器本地 200 并不能证明完全离线或首次公开访问同样快。
- `pokedexClient.ts` 是图鉴资料客户端，不能在没有调用链证据时把其请求计入六卡阻塞。六卡图像是另一类请求，应记录“卡可操作”与“六张图可见”两项时间。

## 最短改进顺序

1. **先量出两条关键路径。**在已有 DEV 调试日志周围以 `performance.now()` 记录 BOOT 预取开始/结束、索引读取、每个候选名额的尝试数及最终成员资料耗时、`FACTORY_SELECT` 提交、敌队预取开始/结束、确认租借、敌队缓存命中与首个可操作命令。网络瀑布按索引、pokemon、pokemon-species、ability、move、图片分类，记录请求数、传输大小及 `X-Content-Store`。只在开发模式采集，避免正式版泄露玩家存档或大量日志。
2. **按实测最长段处理六卡。**若完整成员占主导，保持随机候选与六个名额选取次序，优先把同一成员多个特性的资料并发请求；若仍慢，再把“抽选标识符”和“加工完整资料”分两阶段，冻结随机选择、招式顺序、持有物及 IV 的随机消耗后，以有限并发加工各成员，并按原槽位写回。先写确定性规则回归，避免并发改变六只来源、招式、道具和数值。不要以减少四招资料或默认撞击换速度。
3. **按实测检查敌队预取。**确认预取键与玩家确认时的键一致，且在六卡期间有足够时间完成；若同键仍二次生成，修正失效或竞态。敌队生成也沿用已选单世代池，不能用不同世代的缓存抵消等待。不要为了提速在六卡前同时加载九代资料，避免争夺关键请求与内存。
4. **查本地内容覆盖与回源。**将慢请求的 URL 对照 Go `VERSION/RUNTIME/UPSTREAM`、内容版本与九代索引，优先补缺失的必需数据和浏览器缓存。只有瀑布证明大量独立 HTTP 往返仍是主因时，才评估同源批量资料接口或按所选世代分包；此为后续任务，不作为未经证实的先验方案。保留已实现的 30 秒有界失败和重试反馈。

## 三次中位数验收

先以未改代码的固定提交建立可比基线，再在同一 Go 数据版本、浏览器模拟手机 `390×844`、相同网络节流和无热更新条件下复测。每个世代分别完成三次**冷会话**与三次**同会话热启动**；每次记录构建提交、选中世代、缓存状态、索引与 JSON 数量、`X-Content-Store` 分布、是否有回源及失败。冷会话需新浏览器上下文并清浏览器缓存；若 Go 运行缓存不可重置，明确标成“浏览器冷、服务端热”，不得称为全冷。先覆盖第 1、2、9 代找主因，再以同样方法扫完九代。热更新污染的运行作废重测。

每次计时分为：`BOOT预取开始→预取完成`、`点击开始→六卡可选择`、`六卡可选择→六张图可见`、`六卡出现→敌队预取完成`、`点击确认→首个战斗命令可操作`。另可列“点击开始→首战可操作”，但必须扣开或单列玩家选择停留时间与训练家台词人工停留；此前 13.92 秒只作为未拆分参照。三次取中位数，同时报告最慢单次与各阶段最大耗时，不以平均数掩盖长尾。

建议目标：第 1、2、9 代及其余六代的冷会话六卡可选择中位数 ≤ 6 秒、三次均 ≤ 10 秒；确认至首个可操作命令中位数 ≤ 4 秒、三次均 ≤ 8 秒。若未改代码的三次中位数已优于目标，改动后该指标不得恶化超过 10%；若基线超标，优先修最长阶段并至少降低其中位数 20%。冷会话必需 JSON 不应依赖 `UPSTREAM`；若缺资料，30 秒内结束等待并提供可重试的明确错误。验收每代六只均属所选世代、六选三和首战出招正常，图片与技能/道具资料完整，并附三次原始时间和网络记录，不能只报达标结论。
