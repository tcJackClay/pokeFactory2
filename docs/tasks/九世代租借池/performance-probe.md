# 租借加载单次探针

2026-09-26 在隔离的性能工作树运行开发服务 `:4301`，用两个全新 Chrome 上下文依次完成首次启动、初遇伙伴绑定、设置世代和打开租借六卡。主项目 `127.0.0.1:4300` 的用户存档未访问或清除。探针使用当时的开发埋点；埋点随后以 `6273559` 合入主分支。

| 样本 | 首启默认第一代后台预取 | 改选目标世代后六卡预取 | 点击挑战至六卡可操作 | 记录到的上游响应 |
| --- | ---: | ---: | ---: | --- |
| 第二代，单次 | 1.53 秒 | 3.45 秒 | 3.55 秒 | `pokemon` 244 毫秒、`pokemon-species` 282 毫秒、`move` 392 毫秒 |
| 第六代，单次 | 1.73 秒 | 1.96 秒 | 2.05 秒 | `pokemon` 282 毫秒、`pokemon-species` 940 毫秒；首启第一代的 `move` 503 毫秒 |

两个样本在同一 Go 服务的温热运行缓存下执行。`content-response-in-capture-window` 只说明响应落在捕获时间窗内，不能证明该请求属于所显示的某个槽位；本表也不是冷启动、同条件三次中位数或九世代性能结论。详细临时日志保存在本机忽略目录 `output/perf-probe-gen2.json` 与 `output/perf-probe-gen6.json`，未作为发布工件。

已能确认的缺口是租借过程出现 `X-Content-Store: UPSTREAM`，而发布目标要求从固定版本读取；一些成员处理仍达到秒级。先按 [资料覆盖计划](data-coverage-plan.md) 建立离线覆盖报告并补齐固定版本，再在关闭上游的生产条件下做九代各三次测试。只有固定数据后仍慢，才评估成员加载并发与页面交互优化。
