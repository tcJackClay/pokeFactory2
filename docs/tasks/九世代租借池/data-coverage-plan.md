# 九世代工厂资料覆盖计划

## 当前证据

- `docs/技术差距与实施顺序.md` 的 P0 指出：基础 `backend/config/sync-manifest.json` 仅列宝可梦总表、18 个属性端点及 3 个 CSV；完整同步依赖 `backend/cmd/sync/main.go -full`，尚无公开生产数据版本和关闭上游后的九池实玩证据。
- `storage/data/factorySpeciesIndex.json` 现有 1076 条，按世代为 151、100、138、116、161、79、93、95、143。`-full` 从索引追加 `pokemon/{identifier}` 和 `pokemon-species/{speciesId}`，去重后至少约 1076 个宝可梦键、1025 个物种键，加上基础 19 个 PokeAPI 种子，共约 2120 个初始 PokeAPI 键；递归还会发现招式、特性、形态及进化链。`-max-entries` 默认 20000、`-workers` 默认 6，一旦超过上限，同步失败而不会激活该版本。
- 当前工作区 `var/pokeapi` 只有运行缓存，未见 `var/current.json` 或当前根目录的正式版本清单；不能把运行缓存视为固定发布版本。只读统计得到约 1402 个运行缓存键、70 MB 文件，其中 pokemon 323、pokemon-species 310、ability 200、move 521。按索引条目直接匹配的 pokemon/species 运行缓存覆盖，例如第 2 代约 36/100 与 35/100、第 6 代约 24/79 与 24/79；这只是当前机器的温热缓存，且相同 species 可被多个形态共用，不是发布覆盖率。
- 本地图像报告有 1350 个记录，`storage/assets/pokemon-sprites` 约 4050 张 PNG、173 MB。与工厂索引 `pokemonId` 对照，九代所列物种均有前面图与官方画；背面图第 6 代为 73/79、第 9 代仅 8/143。`backend/internal/assets/sprites.go` 对缺失的背面图和官方画请求都会回退本地前面图，因此这部分不必然破图，但大量第 9 代玩家侧画面会显示正面图；仍须按真实战斗画面验收。图像同步也不在 `-full` 的 JSON 递归范围内。
- 隔离 perf 探针看到 `X-Content-Store: UPSTREAM`、第 6 代单只成员约 1.37 秒；另一次浏览器新上下文但 Go 运行缓存温热时，BOOT 默认第 1 代预取约 1.5–1.7 秒，切到第 2/6 代后点击再生成约 3.45/1.96 秒，第 2 代前两槽约 0.98/1.72 秒、第 6 代第二槽约 1.37 秒，两池仍有 `UPSTREAM`。这些是单次温热环境线索，既非冷启动也非三次中位数。稳定版九池六卡 3.98–20.22 秒的范围也未按数据来源归因。

## 覆盖口径

1. 以索引与现行九代单选规则生成**候选全集**，包含允许的形态标识符，剔除代码明确禁止的物种；保留逐代分母。固定抽样路径的本地 Frontier set、训练家模板及全局回退分别统计，不能只核算某次抽到的六只。
2. 对每个可进入租借或敌队的 `pokemon/{identifier}`，需要对应 `pokemon-species/{speciesId}`、全部可能随机抽到的 `move/{name}` 与每个特性 `ability/{name或id}`。当前四招可能从宝可梦可学招式列表随机选择；只同步一次试玩选出的四招不能覆盖下一次抽样。特殊形态的 `pokemon-form` 与需要的进化链按实际调用和递归链接纳入。用同一版本 manifest 的键集合求差，输出逐代“候选宝可梦、物种、招式、特性、形态、进化链”的应有数、已有数、缺键清单；再与 9 代真机/模拟视口的请求日志交叉核对遗漏端点。
3. 图片另以 `report.json` 的 `local` 路径及文件存在性核算前面、背面、官方画，并对实际战斗/卡片请求 URL 做无上游 GET 验证。缺背面图片的第 6/9 代要记录游戏是否请求及前面图回退的视觉效果；若该回退不符合战斗画面要求，再补素材或调整视觉呈现并验收。图片权利仍属最终发布待决事项。
4. 区分 `VERSION`、`RUNTIME`、`UPSTREAM`、`BUNDLED` 与 404。发布合格要求工厂必需 JSON 均来自固定 `VERSION`，图像来自 `BUNDLED` 或明确纳入发布包的固定版本；不能靠 `RUNTIME` 命中掩盖版本缺口。`/api/content-version` 要显示已激活 PokeAPI、CSV 及素材版本，存档和测试记录附版本号。

## 最小执行顺序

1. **只读盘点。** 写独立覆盖检查脚本读取工厂索引、当前 manifest、宝可梦 JSON 与图像报告，按上述分母列出缺键、缺文件和各世代比例；脚本不得依赖联网，也不得把运行缓存自动算作已冻结内容。先从已抓到的 `UPSTREAM` URL 和第 2/6 代慢槽确认报告能指出缺项。
2. **小范围试同步。** 在独立空状态目录中用少量明确键测试 `PrepareVersion`、递归发现、并发速度、单条体积与失败清理；测实际每分钟键数、峰值磁盘和错误率。再据实测决定 `-workers`、`-max-entries`、代理/限流与存储配额。不要在共享 `var` 上先运行默认 `-full`，也不要在有玩家访问时自动覆盖活动版本。
3. **生成完整候选版本。** 使用单独状态目录和明确版本号运行现有 `-full`，保留同步日志及 manifest；同步过程可能扩展至上万个 JSON 键，默认每请求 Go 客户端期限 30 秒、6 并发，耗时由远端限流和链接闭包决定，无法从本地 70 MB 运行缓存外推出完成时间。准备足够空间容纳下载中的临时对象、完整新版本和可回滚旧版本；粗估至少数倍于实测版本大小，并设实际磁盘阈值，图片包约 173 MB 另计。若 20000 键上限触发，不盲目提高上限，应检查递归是否抓取与工厂无关的大范围链接，必要时缩窄同步器的链接闭包或生成精确清单。
4. **冻结前审计。** 对新版本 manifest 运行完整键闭包校验、文件 SHA256/体积校验，核对 CSV、索引和素材报告与本次构建一致；缺键先补齐再激活。将版本作为发布工件备份并记录总键数、字节数、时长和源时间。`sync` 在 PokeAPI 与 CSV 均准备成功后写 `current.json`；保留旧版本和指针，回滚只切已验证的旧版本，避免仅备份网页而遗漏 `/app/var` 卷。
5. **完全关闭上游验收。** 用生产构建、隔离状态目录的已激活版本与 `ALLOW_UPSTREAM_FETCH=false` 启动 Go 服务，清空浏览器缓存并用新存档逐代各启动三次；执行六选三、敌队加载、进战、出招及图像检查。每次记录六卡与首个可操作战斗命令时间、状态码、`X-Content-Store`、缺资源和控制台错误；九代均不得有工厂必需的 `RUNTIME`/`UPSTREAM` 或 `content_not_synchronized`。另在隔离副本故意移除一个必需键，确认失败反馈及恢复路径。验收结束后保留清单、网络记录、截图与数据版本，交 reviewer 做最终端到端复核。
