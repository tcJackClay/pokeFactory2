# Windows 内容版本发布失败修复计划

## 已确认的事实

- 第六代隔离试同步使用 `-factory-generation=6`，约 1 分 52 秒完成 746 键、25,476,461 字节下载；失败发生在 `PrepareVersion` 的目录发布阶段：`os.Rename(staging, final)` 重试后仍报 `Access is denied`。失败后暂存目录被清理，没有生成可激活版本。该结果不能证明数据闭包或离线发布已经验收。
- `backend/internal/content/store.go` 先将对象和 manifest 写入 `versions/<version>.<时间>.tmp`，随后 `publishVersionDirectory()` 创建同级 `<version>.publish.lock`、检查目标不存在，再调用 `renameWithRetry()`。当前 12 次等待总计约 3.9 秒，末次失败后仍只返回最后一个错误；`syncVersion()` 的无条件 `defer os.RemoveAll(temporaryRoot)` 随即删除可诊断的暂存数据。
- 源码中的 `os.WriteFile()`、manifest 写入和锁文件都在调用目录 rename 前关闭，没有看到明显未关闭的本进程文件句柄；但不能据此排除其他进程对目录或其文件的临时占用。另一个单文件 `rename-probe` 成功，证明同一父目录具备部分改名能力，却不能等价证明刚写完 746 个对象的目录可改名。当前试验现场仅剩单文件探针目录及其锁文件，原失败暂存目录已不存在；无法对那次失败做句柄级取证。
- [Microsoft 的 MoveFileEx 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexa)说明目录移动要求同一驱动器、目标不能是已有目录，改名还涉及删除权限。Go Windows [重命名实现](https://go.dev/src/internal/syscall/windows/syscall_windows.go)调用 `MoveFileEx`。目前暂存与目标在同一 `versions` 父目录，跨卷不符合现场；候选原因依次是短时间的 Windows 文件占用/扫描、目标或锁竞争、特定目录 ACL/安全软件策略。`Access is denied` 本身不能确定是哪一种，需错误码和路径现场证据。

## 最短安全修复顺序

1. **先提高可诊断性。**发布失败时记录版本、源/目标绝对路径、尝试序号、Windows 错误码、累计等待、每次失败后源/目标/锁是否存在及属性。记录对象数与 manifest 总字节；不要输出存档或凭据。目录发布失败时保留当前任务自己的暂存目录和 manifest，返回其路径与“未激活”状态，供重试或人工核查。普通下载/校验失败仍按既有流程清理本次暂存；只对确认位于指定 state 根下的本任务临时目录执行清理，绝不根据字符串拼接删目标版本。
2. **只延长可恢复的同卷改名窗口。**对 Windows 的分享冲突/访问拒绝等可重试错误，在确保目标仍不存在且本进程持有同版本发布锁时，采用有上限的退避，例如总计不超过 30 秒；非可重试错误立即失败。若目标在任一轮出现，停止，不尝试覆盖、合并或删除。现有约 3.9 秒窗口可能短于扫描占用，但“扫描导致”仍只是待验证推断。保留同一父目录的原子目录移动，不引入复制回退。
3. **给保留的暂存目录提供受限的重新发布入口。**该入口读取暂存 manifest，逐对象校验 SHA256 与路径，检查版本尚未存在、暂存确属隔离 state 的 `versions` 子目录、没有活动指针指向半成品；重新获取同版本独占锁后执行不可覆盖的目录发布。成功后复核最终目录及版本清单，再由现有激活前覆盖校验决定是否切 `current.json`。操作员可在解决占用后复用已下载的 25 MB 数据，无需自动重抓；失败仍保留暂存并报告。不能把旧失败目录当成已准备好的版本。
4. **只有真实大目录仍稳定失败，才设计第二发布机制。**可在持有独占锁且 `final` 不存在时，以原子创建方式独占一个新的最终版本目录，复制暂存对象，逐文件校验，最后写完整标记；激活逻辑只接受完整标记和通过覆盖审计的版本。进程崩溃留下的未完成目录标为孤儿，下一次发布不得合并、覆盖或自动删除它，应由独立的、按绝对路径核验的清理流程处理。此方案需要额外磁盘和测试，不能恢复旧的“改名失败就复制进已有目标，失败再删除目标”回退。

对不可覆盖语义应进一步收紧：发布目标即使被不遵守锁的外部进程创建，也不得被替换。Windows 上可选用不带覆盖标志的目录移动 API；跨平台实现也应有等效的不可覆盖保证或显式说明并测试。仅做 `os.Stat(final)` 预检查不足以证明并发下永不覆盖目标。

## 验证

- 在 Windows 本地临时目录构造接近第六代的多层 746 对象与约 25 MB 数据，不联网；验证正常发布、短暂持有文件/目录句柄后释放的恢复、持续占用时 30 秒内失败且源和已有目标不变。单文件探针不作为充分验证。
- 对同版本并发两个发布者、预先存在空/非空目标、锁文件已存在、权限拒绝、异常中断分别测试：不得覆盖/合并/删除目标，未完成内容不得写 `current.json`，失败保留明确可识别的暂存记录。已有 `TestPublishVersionNeverMergesIntoExistingDirectory` 与 `TestPublishVersionRejectsConcurrentReservation` 应保留并扩充大目录及 Windows 句柄场景。
- 仅在小型隔离试验和 Windows 大目录本地测试通过后，再以全新隔离 state 复跑第六代同样参数。要求得到非空 PokeAPI 与 CSV manifest，激活前校验通过，`/api/content-version` 指向该版本；关闭上游、清运行缓存后请求样本返回 `X-Content-Store: VERSION`。复跑不得写共享 `var/current.json`，也不得自动清理旧失败路径。
