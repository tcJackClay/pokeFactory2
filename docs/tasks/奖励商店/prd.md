## 2. 领域口径（实现前必须理解）

### 2.1 货架件数为什么必须 6，以及为什么必须 9 种持有道具

- 同一种持有道具整局**最多 1 件**，只可能存在于「某名队员身上」或「商店候选名单」两处之一。
- 开店瞬间，**三名队员恒占 3 件**（`factoryEquippedHeldItemId`，本局返还基准）。
- 所以：**可摆出的持有道具件数 = 候选种类数 − 3**。
- 要**只靠持有道具**就摆满 6 件 → 种类数 ≥ **9**。7 种时只能摆 4 件。
- 技能机首版 0 台上架；进化道具只在队里有人用得上的时候才进候选。两者都**不能**用来保底。

### 2.2 商品三类

| 类别 | 是否占用「同一种类 1 件」的名额 | 兑换后 |
| --- | --- | --- |
| 持有道具 | 占用 | 选一名队员装备；若该队员已有持有道具，先确认替换；换下来的**不进背包** |
| 技能机 | — | 首版 0 台上架，本次**不实现**任何技能机（不得用旧奖池或未验收招式顶替） |
| 进化道具 | **不占用**（当场消耗掉） | 选一名**用得上的**队员；该队员立刻进化；道具消失，不回商店 |

### 2.3 稀有度三档（唯一数值源必须是配置，不得写死在 UI）

| --- | --- |
| 稀有度 1 | 1 券 |

### 2.5 兑换券

- 数据字段已存在：`runSupply.tickets`（界面旧文案「本局补给券」）。**每胜 +1，已有实现，不要改。**
- 券是**玩家当前余额**，兑换时扣。余额不足的商品在界面上**点不动**。
- **一组七战打完**：组末结算时把剩余券按 **1 券 = 1 BP** 并入本次结算，**计入 `MAX_FACTORY_BP`(9999) 上限**；随后券清零，下一组从 0 张重攒。
- **一组中途败退**：券直接清零，**不折算、不给 BP**（`createEmptyRunSupply()` 现有行为，保持不变）。

### 2.6 进化道具的 39 种与 94 条关系

- **完整逐条映射**（哪只宝可梦用哪件道具进化成什么）已从指定 Rogue `expansion` 固定源码重新生成：`docs/tasks/扩池规则/evolution-items.generated.md`。94 条包括觉醒之石的性别限定关系；王者之证首版只作持有道具，其两条进化关系不计入。
- 数据来源是用户指定的参考项目 `Pokabbie/pokeemerald-rogue`（及其上游 `reference/pokeemerald-expansion`）。**不得自行编造**参考项目里没有的进化关系或道具。
- 该参考项目把「通讯交换进化」实现为**使用连接线道具**（`include/constants/pokemon.h` 把 `EVO_TRADE` 与 `EVO_ITEM, ITEM_LINKING_CORD` 并列写在同一批宝可梦上）。本项目照此口径：**连接线就是一件普通道具，用它进化，不需要真的交换。**
- **王者之证 `kings_rock` 双重身份的处理（已定）**：它在参考项目里既是持有道具，又是**蚊香君 → 蚊香蛙皇、呆呆兽 → 呆呆王**的道具进化条件。本项目里它已是商店的持有道具（2 券），**首版只当持有道具**，这两个进化**换不到**。实现时必须在候选枚举里显式排除，不得让它同时以两种身份出现。

## 3. 功能需求

### F1 · 商店界面（目标 A）

1. 商品**恰好 6 件**（配置项驱动，不写死数字）。
2. 每件显示：图标、中文名、**价格（几券）**、**能拿它做什么的一句话说明**。说明文案必须是**由数据驱动**的（见 F5）。
3. 界面必须显示**当前券余额**。
4. 券够 → 「兑换」可点；券不够 → **点不动**且视觉可区分（不是禁用错误提示）。
5. **一次可买多件**：买完一件后界面回到商店，券余额刷新，未买的商品仍在（**货架不重新配货**）。
6. **可以一件不买直接离开**，且离开后正常推进战次。
7. 6 件商品之间**互不重复**（同一 `itemId` 不得出现两次）。
8. 图标缺失时**不得出现破图**（复用既有图标兜底逻辑）。

### F2 · 配货（目标 A/D）

1. 候选 = `持有道具候选(9 种) − 三名队员当前返还基准` ∪ `队里用得上的进化道具`。
   - 「返还基准」只读 `factoryEquippedHeldItemId`，**不得**读本场当前持有物 `factoryHeldItemId`。
2. 从候选里**不放回随机抽 `shelfSize`(6) 件**，每件机会相同。**不规定**「几件持有道具配几件进化道具」。
3. 因为 `9 − 3 = 6`，**持有道具这一类自己就足够摆满 6 件**：货架**永远能摆满 6 件**。若因任何原因算出来不足 6 件，视为**缺陷**（不是正常分支）：不得用重复商品、未验收技能机、旧奖池或空货位顶替，也不得悄悄少给。
4. 货架一旦摆出即**冻结**：刷新、关掉重进、同版本导入存档后，**逐件不变**（含价格与顺序）。

### F3 · 兑换交易（目标 B）

1. 点「兑换」→ 先扣券、再交货，**要么全成、要么全不做**（不得出现扣了券没给东西，或给了东西没扣券）。
2. **同一件商品只能兑换成功一次**：双击、连点、刷新、导入存档四条路径都不得重复扣券或重复入账。
3. 持有道具的兑换：选一名队员装备；该队员已有持有道具时先确认替换；旧的那件**不进背包**，且**立刻回到候选名单**。
4. 兑换后仍须满足「三名队员的返还基准互不重复」这条不变量；外部导入的存档若出现重复，保留既有修复逻辑的行为（保留下标最小的那件并如实提示，不报错中断）。
5. 券余额**不得为负**。
6. 兑换失败（如无合法装备对象）必须可恢复：留在商店，可重试，**不推进战次、不少给、不重复给**。

### F4 · 进化道具的兑换与进化（目标 E）

1. **候选资格**：只有「队里存在一只宝可梦，用它确实能进化」时，这件道具才进候选。没人用得上的道具**不得**上架。
2. **兑换流程**：选一名用得上的队员 → 该队员立刻进化 → 道具被消耗（不回商店）。
   - 多名队员都能用同一件道具时，必须让玩家**选择**其中一名；只有一名符合时可直接确认，但仍须显示进化的前后形态。
   - 同一只宝可梦可能需要同一件道具的多个进化分支（如伊布用火之石只能进火伊布，唯一）——按数据来；若数据给出多个目标，必须由玩家选择，不得静默取第一个。
3. **进化结果**：
   - 物种变为进化后的物种；**等级、个体值、努力值、性格、性别、异色等既有属性不得被重置**。
   - **必须保留原来的四招**（逐招、按原顺序一致）。**严禁**走现有 `getProcessedPokemon` 那条「重新随机抽四招」的路径。
   - **持有的持有道具不变**：进化**不得**改动 `factoryEquippedHeldItemId` / `factoryHeldItemId`（进化道具与持有道具是两套东西）。
   - 进化**不得**影响「同一种类持有道具整局 1 件」的不变量。
4. **跨组保持**：进化跟着队员走。打完一组进入下一组、存档读写、导入导出之后，**仍是进化形态**，不打回原形。
5. **进化道具用掉后**：该件道具不得再次出现在候选里（因为队里已无人需要它，自然出局；但仍须有明确断言，不得靠副作用）。
6. **血与 PP 不做额外处理**：每场开战前队伍自动回满，商店开在战后，本来就是满的。

### F5 · 商品说明诚实性（延续既有硬规则，已在 `dev` 实现）

1. 允许摆出「能装但这一局用不上」的持有道具，但**说明必须如实**。
2. 已有的三态判定 `getRewardApplicability` → `APPLICABLE` / `CONDITIONAL` / `NO_TRIGGER` 必须继续驱动文案，且扩展到新增的两种香草：
   - **白色香草**：持有者任一能力等级低于初始值时才有收益，下降可由对手或自身招式造成 → `NO_TRIGGER`（当前确无下降场景）或 `CONDITIONAL`，**不得**标成无条件有效。
   - **心灵香草**：只有对手造成过妨碍状态（挑衅、再来一次等）才有收益 → 同上。
3. **进化道具**的说明必须是**具体**的：至少写出「用它把谁进化成谁」。多名队员可用时列全。不得写「可以进化宝可梦」这类空话。

### F6 · 白色香草的战斗效果（目标 D，当前缺失）

- 现状：`src/features/game/data/battle/itemEffects.ts` 声明了 `white_herb`（`effectId: 'WHITE_HERB'`，`hooks: ['restore-lowered-stats']`），但**全库没有任何一处战斗逻辑响应它**（对比：`mental_herb` 已在 `useBattleController.ts` 接好）。
- 要实现的行为：**持有者任一能力等级降至初始值以下时，复原所有低于初始值的能力等级，并消耗掉白色香草**。自身招式造成的下降也触发，正值不变；没有负值则不消耗。
- 判定口径、触发时机、消耗语义必须与参考项目一致；要与 `mental_herb` 的现有实现风格保持一致。
- 必须有确定性单元测试；并且**在浏览器实玩里真的触发过一次**（见验收 AC-9）。

### F7 · 组末券折算 BP（目标 C）

1. 触发点：**七战整组获胜后的结算环节**（`commitFactoryGroupSettlement` 所在路径）。
2. 计算：`折算 BP = 该组结算时剩余的券数`（1 券 = 1 BP），并入同一次结算。
3. BP 结果必须**受 `MAX_FACTORY_BP`(9999) 上限约束**（先加折算、再钳位；或等价口径，但必须可验证）。
4. 折算后券清零，下一组从 0 张重攒。
5. **中途败退**：券清零、**不折算、不给 BP**（保持现有行为）。
6. 必须能区分出「本次结算里有多少 BP 来自券折算」，以便验收（如结算结果字段或日志）。

## 4. 非功能需求

1. **门禁全绿**：`npm run lint`（tsc）、`npm test`、`npm run build`、`go test ./...`。既有 2 项 `go test` 失败是 Windows 符号链接权限问题，与本任务无关，忽略但要如实记录。
2. **存档兼容**：老存档（含四卡检查点的存档）读入不得崩溃；字段缺失要有安全默认。若存档结构有版本号，按既有版本策略处理。
3. **不越界**：不得顺手改战斗数值、强度分档、队伍生成规则、物种池规则。
4. **不引入未验收内容**：不得启用任何技能机、不得启用被排除的光粉 `bright_powder`。
5. **单一数值源**：货架件数、价格档位、持有道具候选名单、进化道具名单都必须是配置/数据文件里的唯一来源，UI 不得内联硬编码。

## 6. 明确不做（本次范围外）

- 技能机上架（0/50 通过）——货架不依赖它。
- 光粉 `bright_powder`。
- 属性强化道具 1.2 倍（decisions.md 第 2 条，待用户点头）。
- 气势头带是否消耗（第 3 条，待用户点头）。
- 基地商品与价格。
- 进化道具的**多步**进化（一次兑换只进化一步）；`王者之证` 的双重身份。
- 实体手机验收。
