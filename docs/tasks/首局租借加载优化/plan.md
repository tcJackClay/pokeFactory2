# 首局租借加载优化实施计划

## 第一世代阻断诊断

- 最新浏览器验收：第一世代新档两次等待约 2 分钟仍停在“正在寻找宝可梦”；一次在 25 秒时累计 236 请求，其中 235 个为 200，未见脚本错误。此前第九代约 11～14 秒能显示六卡。只有请求总数而无瀑布详情，不能判定是哪条请求最后未完成；某一时刻剩一条 pending 也可能是串行链不断推进，不等于该条永久挂起。
- 本地 `storage/data/factorySpeciesIndex.json` 可静态复核：第一代 151 条，Lv50 第一档 BST 220–430 且 `BASE` 的 53 条；第九代分别为 143 条、30 条。初租借只需六只、禁用 Unown 201，故“第一代基础候选不足”不是首要解释。`buildFactoryPool` 的 150 次尝试限制只限循环次数；循环每次 `await` 仍可无期限等待。
- `src/services/pokeApiEndpoint.ts` 的 `fetchPokeApiJsonFromUrl` 直接 `fetch`，无 `AbortSignal`/单请求超时；`factorySpeciesIndex.ts` 的索引请求同样无超时。`pokeApi.ts` 的 `getProcessedPokemon` 先顺序等待特性资料，再逐个等待四个招式，六个成员也顺序处理，任何 pending 会阻塞整池。Go 默认上游 client 20 秒超时、HTTP 写超时 60 秒，但前端没有整次租借生成的期限；本地缺数据并允许回源时，三个前端重试还会叠加后端等待。
- BOOT 只启动后台预取，不等结果。若预取最终失败，`prefetchRentals` 吞异常返回 `false`，`startGame` 在同一次点击中再完整调用 `generateRentalDraft`；失败仅写 console，`App.tsx` 的 loading 只显示通用文案。这会放大慢路径并令玩家不知道发生什么。

先用浏览器网络瀑布和工厂阶段计时辨别索引命中、候选尝试数、最终宝可梦资料、特性、招式与回源状态。不能仅根据 235 个 200 响应就放宽第一代玩法筛选。

## 现状与等待链

- 本任务以已定的九个互斥世代池为前提：设置单选一个世代，当前扩展规则从这一代随机生成六只租借。固定 Frontier set 不覆盖全部九代，不能靠打开 `useReferenceSetPool` 解决本任务，也不得改变抽样权重、招式或持有物结果来换速度。
- `usePokeFactoryGame.ts` 在 BOOT 阶段发起 `prefetchRentals()`，但不等它完成就显示基地；玩家点击开始后，`useFactoryFlow.ts` 的 `startGame()` 等待同一预取，若失败还可能再调用 `generateRentalDraft()`。玩家感受到的等待因此取决于后台预取完成度。切换世代时已有 token 与缓存键失效逻辑，应保留。
- `generateRentalDraft()` 调 `buildFactoryPool(count=6)`。每个名额以最多 `2+qualityBias` 个候选随机取样，循环中顺序读取候选元数据、按 BST 与进化阶段筛选，然后顺序调用 `getProcessedPokemon()`。最多 `count*25` 次尝试。`getFactoryCandidateMeta()` 优先查询一次性 `/api/data/factory-species-index`；不可用时退到 `pokemon`、`pokemon-species` 和进化链请求。此索引是减少候选探查请求的关键，应先查覆盖率与失败情况。
- `pokeApi.ts` 的 `getProcessedPokemon()` 读取 `pokemon`、`pokemon-species`，`fetchPokemon()` 的详情填充还逐个等待特性名称；随机招式循环逐个等待最多四个 `move` 详情。六个最终成员之间同样串行。内存有宝可梦、物种、特性和招式缓存，端点层对同路径进行进行中去重，但招式缓存本身未存进行中的 Promise。`pokedexClient.ts` 是图鉴的独立客户端和缓存，并非租借生成主链；不可把图鉴预载当成本任务优化已完成。
- Go 同源服务提供 `/api/data/factory-species-index`、`/api/pokeapi/*`、`/api/pokeapi-sprites/*`。`backend/internal/content/store.go` 可读本地版本化内容缓存并合并并发同键请求；`backend/internal/web/app.go` 可按配置允许上游回源，静态精灵图先走本地素材库。浏览器中的 `/api/pokeapi/*` 成功请求不等于离线数据一定完整，须读取 `X-Content-Store`、状态码和本地内容版本。图片地址包含在资料里，卡片图片由浏览器渲染请求；应把 JSON 等待与图片加载分别计时，确认图片是否阻止六张卡可操作。
- 已有 `390×844` 模拟手机基线：三次初租借约 10.1、10.2、12.9 秒，分别 148、126、125 个本地 `/api/pokeapi/*` 成功响应（`docs/tasks/基地钱包持久化/runtime.md`）；v9 七战样本首次约 24.7 秒，后续 v10 第九代样本约 11～14 秒（`docs/tasks/组末BP结算/runtime.md`），两者均未完整记录对应请求数，不能凭耗时断言单一原因。这些都是浏览器模拟视口，尚无实体手机计时。

## 最短实施顺序

1. **先解除第一代阻断。** 为索引和资料请求建立有界超时、可取消或失效的请求令牌，并为整次六卡生成设上限；超时后结束 loading、显示错误和重试操作。共享进行中请求的取消不得误伤其他消费者，旧请求返回不得覆盖新世代或重试结果。同一次点击若预取失败，只报告失败，不再隐式完整重跑一轮。先用第 1 代冷档复测，确保成功或有界失败；此步不改池、BST、招式或道具规则。
2. **补可定位的计时。** 在预取入口、候选元数据、完整成员加工、招式/特性/物种资料与六卡提交处记录耗时、尝试次数、实际候选数、缓存命中、请求数及数据来源；浏览器 Performance 网络记录区分 JSON、图片、冷缓存、热缓存、失败重试。记录选中世代、构建版本与 Go 内容版本，不打印存档敏感内容。分别重测第一代及第九代的冷启动，解释现有 11～24.7 秒波动，再定最大等待段。
3. **保持抽样顺序，缩短资料阻塞。** 继续用现有工厂物种索引完成候选筛选；只对最终选定的六个标识符加工详情。优先把相互独立的 `pokemon`/`pokemon-species`/特性/招式详情请求合并为有界并发，复用同路径 Promise；组装阶段仍按已选编号和原随机招式顺序写回。不得直接砍掉招式、用默认撞击掩盖资料错误、删去持有物或改变六只的物种抽样分布。为避免并发随机数调用改变可复现结果，先冻结本次选中的标识符与招式候选顺序，再并发取资料。
4. **补齐本地内容并检查传输。** 校验 `factory-species-index` 覆盖九代与特殊形态的实际候选，Go 内容版本覆盖最终成员常用的物种、特性、招式；缺数据以明确错误返回。按计时结果再考虑由 Go 提供批量资料端点或预生成轻量战斗资料包，按世代分块而非首屏下载九代全集。复用现有同源 API、内容版本与浏览器缓存；避免把上游回源变成公开玩家首局的隐形前提。

主要修改入口：`src/features/game/hooks/useFactoryFlow.ts`、`src/services/pokeApi.ts`、`src/services/pokeApiEndpoint.ts`、`src/features/game/config/factorySpeciesIndex.ts`、`src/features/game/hooks/usePokeFactoryGame.ts`、租借等待 UI、`backend/internal/web/app.go` 与 `backend/internal/content/store.go`。只有计时证明单请求 RTT 或数据缺口是主因时才新增 Go 批量端点；先消除前端串行等待。

## 验收

- 保持单世代来源：对九个世代分别固定随机种子生成六只，物种均属所选池（已定义的同代特殊形态按其世代），无不允许的重复；记录前后同种子生成的物种、招式、持有物与战斗数据差异，除明确批准的错误修复外应一致。进战正常出招、读取技能说明、图像正常显示，不能以降质资料换时间。
- 性能目标以本地完整内容、`390×844` 模拟手机、同等网络限速和无开发面板干扰测量：第九代冷启动从点击“开始挑战”到六卡可操作，三次中位数不高于 6 秒、最慢不高于 10 秒，JSON 请求数不高于 80；同一会话热启动三次中位数不高于 3 秒。与旧 10–13 秒/125–148 请求、v9 的 24.7 秒及 v10 的 11～14 秒并列报告。若预取在点击前已完成，另报从 BOOT 到预取完成的总耗时，不能只用近零点击等待掩盖后台成本。图片首屏可见时间另列，不混入 JSON 指标。
- 关闭 Go 上游回源或让一项必需资料缺失，验证六卡不会悄悄降为错误招式/空图、不会无限转圈，玩家能看到错误并重试；恢复服务后成功。验证切换世代时旧预取不污染新池。
- 第一代阻断回归：分别模拟索引、宝可梦、物种、特性和招式请求永不完成，确认每项都能在设定期限内结束 loading、显示可重试错误，且一次点击不会暗中生成第二轮。用真实第一代新档重复三次，记录六卡成功或明确失败的时间、请求路径和 `X-Content-Store`；150 次尝试上限与总时间上限都须生效。
- 运行定向测试、类型检查、构建及 Go 服务测试。以 `390×844`、`320×568`、`844×390` 视口实玩开始挑战、六选三、第一战，并在实体手机浏览器复核冷/热等待、图片、触控和失败提示，附网络瀑布与时间戳证据。
