# 功能规格

> 读了这一节，architect 就能拿到本任务所需的全部玩法规则。

## 1. 触发条件

每组七战。当该战在组内的序号 ∈ `{4, 7}` 时，进入**该战的战前阶段**：玩家先完成「换怪或跳过」，随后打开四卡奖励节点。

即：**胜第 3 场 → 第 4 战开战前**；**胜第 6 场 → 第 7 战开战前**。等价于「每组第 3、6 胜后四选一」。

配置事实（已存在于 `dev`）：`FACTORY_REWARD_CONFIG = { battlesPerSet: 7, freeRewardChoiceCount: 4, preBattleRewardBattlesInSet: [4, 7] }`。

## 2. 初始状态

- 节点状态 `PENDING`。
- 队伍三名队员各持有一件「**本局返还基准**」持有物：初始为租借原配；此前领过奖励装备的成员则为该奖励装备。
- **无候选池缓存、无「已获得」台账**——候选池每次进入节点时按当前装备实时重算。

## 3. 流程

### 3.1 候选枚举

**持有物候选 = `H \ E`**

- `H` = **基础保底七件**（本任务 `H` 恰为此七件）：
  `scope_lens`、`quick_claw`、`kings_rock`、`choice_band`、`focus_band`、`heavy_duty_boots`、`loaded_dice`
- `E` = 三名队员**本局返还基准**的持有物 ID 集合（去重）。
  - **必须用「本局返还基准」计算，不得用「本场当前持有物」**——否则战斗中被打落/消耗的那件会被误判为空位，从而放出重复卡。
  - 已确认：`load` 时初始为租借原配；领取奖励装备后更新为该奖励装备。
- 排除集合：`E` 中的 ID 一律不出卡。**对原持有人「原物再装备」不算可领取**（因该 ID 已在 `E` 中）。
- 数量下界：`|E| ≤ 3` 且互不重复 ⇒ `|H \ E| ≥ 7 − 3 = 4`。

**唯一性与回池（用户决定 2026-09-27）**

- 单一种类道具在整局中**最多只存在 1 件实例**；该实例只能在「**在队**」（装备于三名队员之一）与「**在池**」（候选）之间转移。
- **候选池 = `H` − 当前在队装备集合**；道具被**替换**或**主动舍弃**后**立即回池**。
- **不落任何持久化「已获得」台账**，也不用「本局已出过卡」的历史做去重。
- **不触发回池的情形**：战斗中被打落/消耗属「暂时不在手」，按既有「下一战开战前按本局返还基准返还」语义该件**仍在队**，不回池。

**TM 候选**

- `TM 候选 = allowlist ∩ 当前队伍可学 ∩ 未掌握`。
- 当前 allowlist 为 **0/50**，故本任务 TM 候选**恒为空集**。这是可接受的：四卡保底**独立于 TM**。**不得**用未验收 TM 或旧 `getLearnableMoves` 全量抽样作为候选来源。

**其他类别**

- 首版**无此类**。`battle_atk`（力量强化）/ `battle_def`（防御强化）已按用户决定从项目删除；不得以「出现在商店/数据表」为理由新增类别。

### 3.2 过滤（合法性）

- 每张候选必须**至少存在一个合法装备对象**：即存在某名队员 `i`，把该道具装备给 `i` 后，三人返还基准仍**互不重复**。
- 在 `|E| ≤ 3`、`H` 内 ID 互异、候选 ∈ `H \ E` 的前提下，任选一名队员装备后其基准仍是 `H` 中的另一 ID，与另两人必不相同 ⇒ **恒有合法对象**。此结论须由代码断言而非默认假设。

### 3.3 抽样

- 从合格候选集合中**不放回等权抽 `min(4, |候选|)` 张**（`4` 取自 `freeRewardChoiceCount`）。
- 本任务在七件、3 件在队时，候选恒为 4 ⇒ **恒抽满 4 张**。
- **不固定 ITEM / TM 配比**（orchestrator 裁决 2026-09-27，采纳 designer 建议）。理由：TM allowlist 尚未齐备，固定配比会新增「某类下限不足」的失败点。
- 权重与池配置须**独立**：不得沿用旧 `FREE_REWARD_TYPE_WEIGHTS`、旧 `POKEMON`/`EVOLUTION` 池、也不得沿用旧「十次重抽」路径。

### 3.4 冻结

- 候选生成后写入存档，节点状态 `PENDING → READY`。
- **刷新、重开、同版导入必须保留已展示的候选，不重新抽取。**

### 3.5 领取

- 玩家从 4 张中选 1 张。
- 选择装备对象（租借队三人之一）。
- 若该队员已有持有物 ⇒ 提示**替换**；确认后**旧物直接移除、不进背包**，并**回池**。
- 状态 `READY → CLAIMED`（原子），新物写入该队员**本次挑战后续每战开战前的返还基准**并即时显示为当前装备。

### 3.6 卡面诚实性（硬规则）

- 允许出现「**可装备但当局无触发场景**」的卡片。此时卡面/选择提示必须**如实标注适用性**：
  - `heavy_duty_boots`：仅在**入场时已铺设入场陷阱**（本项目现支持隐形岩、毒菱）时有收益；**接地毒属性仍吸收毒菱，不跳过该吸收**；**不得**宣称覆盖尖刺/黏黏网等未实现陷阱。
  - `loaded_dice`：仅在持有者**已装备合格的 2–5 次连续攻击招式**时改变次数；无此类招式时**无收益**，须呈现为「可装备，但当前无对应触发场景」。
- **不得为凑满四张而谎称当局一定有效。**

## 4. 终态

- **`CLAIMED`**：领取成功，节点结束，进入第 4 / 第 7 战。
- **失败**（候选枚举失败 / 存档写入失败）：**留在奖励节点可重试**，语义为「**不推进战次、不少给卡、不重复卡**」。
- **重置 / 退出**：回到基地，节点状态随挑战一并丢弃。

# 边界情况

> orchestrator 拥有。上游规则未覆盖但本实现必须处理的边界。

**候选不足要三分，不得混为一谈**

- **(A) 数据/加载/计算失败** ⇒ 错误路径：留在节点、给可重试反馈，**不推进战次、不少给卡、不重复卡**。
- **(B) 因产品边界导致 `|候选| < 4`** ⇒ 在七件保底下**不应发生**。若发生，**明令禁止**用重复卡、不可学/未验收 TM、旧奖池、空卡填空，或隐式少给卡；必须作为缺陷上报，**不得由代码静默补位**。
- **(C) TM 候选为空** ⇒ 正常，不视为失败。

**持久化与竞态**

- 刷新 / 重开 / 同版导入：`READY` 候选**冻结不重抽**；`CLAIMED` **不得重复领取**，也不得复活被消耗/拍落的旧装备。
- 双击 / 连点：**只领取一次**（不依赖 UI busy 标志）。
- 处于 `PENDING`（尚未生成候选）时刷新：重新生成即为合法，因为是同一节点、同一队伍状态。

**装备与唯一性**

- **换怪后**必须**先核验整队返还基准唯一性，再重算候选**；不得擅自丢弃敌方原配道具。
- 战斗中**被打落/消耗不触发回池**（该件仍在队）。
- 「原物再装备」不算可领取（该 ID 已在 `E` 中，天然被排除）。
- 三人返还基准**互不重复**是本任务的不变量，任何写入路径都必须维持。

**存档兼容**

- 旧存档若含 `battle_atk` / `battle_def` 或旧奖池 ID，必须**安全丢弃、不崩溃**（既有 `hydrateInventoryFromItemIds()` 已具备该容错，须保持）。
- 项目约定：**本轮修改不要求兼容过往存档**，但必须在清除或拒绝前给玩家明确提示。

**阶段切换**

- `stage` / `battleEpoch` 变化时**重算候选**，不得跨奖励节点复用旧候选集合。

# 验收条件

> 可判定的玩家可见结果。architect 会把它翻译成 `plan.md` 的验证计划。

1. **四卡保底**：三人装备七件中的**任意三件**、且 TM 候选为 0 时，节点仍产出 **4 张 ID 互异、无同名、每张至少一个合法队员**的卡。须以**逐队枚举/确定性夹具**证明，而非抽样观察。
2. **返还基准口径**：战斗中消耗/拍落**不改变候选**；换怪后**重算**且保持三人唯一。
3. **冻结**：生成候选后刷新、重开、同版导入，候选**逐张不变**。
4. **唯一领取**：双击与连续点击同一次领取，**只产生一次** `CLAIMED`、装备位只变一次、旧物不回背包。
5. **替换与回池**：领取并替换后，旧物**回到候选池**（可在后续节点再次出现），且三人返还基准仍互不重复。
6. **返还时序**：领取的新物成为该队员**下一战开战前**的返还基准；第七胜后无下一战时**不提前返还**。
7. **失败语义**：注入候选枚举或存档写入失败，节点**留在原处**、战次不推进、不出现少给卡或重复卡。
8. **卡面诚实**：`heavy_duty_boots` / `loaded_dice` 在无触发场景的队伍中**不宣称当局有效**。
9. **端到端**：在模拟手机视口完成「胜第 3 场 → 换怪/跳过 → 四卡 → 选卡 → 选队员 → 替换确认 → 第 4 战开战前返还」全链路。
10. **静态门禁**：`npm run lint`、`npm test`、`npm run build` 全部通过，且**新增测试覆盖上面的逐条断言**。

# Orchestrator 裁决补遗（2026-09-27）— 阻断项修复

auditor 判 **不 PASS**，阻断项为：**三人返还基准唯一性未在每条写入路径上维持**。

- 守卫只挂在「奖励前那一战」（stage 3/6 胜后）；第 1/2/4/5 胜后的换怪无守卫，`commitFactoryBattleStart` 亦不校验。
- 后果：可写入三人基准重复的队伍 ⇒ 之后第 3/6 胜后 `commitFactoryRewardPending` **必抛错**，且重试与「跳过换怪」都不可通（仅能靠再换一次怪逃逸）。这是**不可恢复状态**，违反 PRD「任何写入路径都必须维持」与「失败语义」。
- 可达性不低：set 1 下玩家租赁 `pool[0..5]` 与敌方 `pool[0..2]` 天然同款。

## 一、本裁决要求的效果（implementation 自选）

1. **不变量**：三名队员的**本局返还基准**在**任何时刻、任何写入路径**上互不重复——包括 `load`/旧档迁移、换怪（全部胜次，不只奖励前）、奖励领取、逐战返还。
2. **不可恢复状态必须消除**：到达奖励节点**绝不允许死路**。即使数据层出现重复（例如外部导入的存档），系统必须**可恢复并如实提示**，不得以抛错终止、不得卡住重试与跳过。
3. **不得静默侵占玩家资产**：不得自动替换、不得擅自丢弃任何一方原配道具（含敌方）。
4. **不得静默补位**：候选不足时仍不得用重复卡/未验收 TM/空卡填空。

## 二、对先前裁决的修正

先前「风险 3」裁定为「本次不改 `FACTORY_BATTLE_CONFIG.heldItemPool`」。**该裁定的适用范围收窄为：池子的「名单内容」不变。**

现在**允许**为实现上述不变量而**在生成期增加排除逻辑**（例如让敌方/换怪来源不携带玩家队当前持有的道具）。依据：`docs/tasks/扩池规则/decisions.md` §10 已记录参考实现的同款行为——`battle_factory.c:297/458/698` 阻止敌方队伍生成与玩家队相同的持有物，其目的正是「保证战后任何换怪都不破坏 Item Clause」。因此这不是新增机制，而是**本项目已记录的参考行为的落地**。

附加约束：该排除逻辑**不得**导致生成失败或无解（例如候选耗尽时必须能优雅退化），且**不得**改变敌方强度分档与队伍构成规则。

## 三、连带处理（非阻断，一并修掉）

1. `getFactoryRewardApplicability` 与 plan 命名漂移、且**生产未接入** —— 须使卡面诚实标注**实际由该判定驱动**，并统一命名。
2. 四卡数量 `cards.length !== 4` **硬编码** —— 须联动 `FACTORY_REWARD_CONFIG.freeRewardChoiceCount`。
3. `loaded_dice` 的适用性谓词与引擎 `resolveMoveStrikes.ts:56` **不完全同构** —— 须对齐（含 `SKILL_LINK` 情形，宁可少报不可错报）。
4. 「无合法装备对象」抛错分支在 3 人/七件口径下不可达 —— 保留该防御断言，并**补一条可直达该分支的单元测试**（直接构造重复基准输入）。

## 四、修复后的验收

修完必须**重跑三项静态门禁**，并**新增覆盖以下情形的测试**：

- 第 **1、2、4、5** 胜后换怪引入重复基准时的处理（不得写入重复队伍）。
- `commitFactoryBattleStart` 对不变量受损的输入的处理（可恢复、不抛错终止）。
- 第 3/6 胜奖励节点在**曾经换过怪的队伍**上仍能正常生成四张、不出现死路。
- 注入「重复基准的存档」后加载 / 导入：可恢复并如实提示，不崩溃。
