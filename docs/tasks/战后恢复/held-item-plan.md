# 工厂战间持有物返还计划

## 原型与当前差距

`reference/pokeemerald-expansion/src/battle_factory.c:609–623` 的 `RestorePlayerPartyHeldItems()` 按租借 set 记录重新赋予玩家队伍持有物；`data/maps/BattleFrontier_BattleFactoryPreBattleRoom/scripts.inc:56` 在下一场战斗的前战室调用 `factory_resethelditems`。用户最新明确：**持有物在下一场战斗前返还**。战斗中、赛后结果页及换怪页保留本场消耗或拍落后的当前状态；下一场开战时，对象是届时的玩家租借队，包含已交换获得的成员。HP、PP 与异常状态的战后恢复另按既定规则处理。

当前 `useFactoryFlow.ts` 在建池时仅把选出的 `itemId` 写入可变 `GamePokemon.factoryHeldItemId`。`useBattleController.ts` 的消耗与拍落会将此字段设为 `undefined`；没有保留初始持有物来源。`restoreFactoryParty.ts` 已负责战后 HP、PP、异常与临时状态恢复，并在 `resolveBattleResult()` 成功结算后、进入 `ROUND_RESULT` 前被调用；`performSwap()` 也复用它，但不会恢复已清空的持有物。`saveManager.ts` 会保存战斗队伍，却没有原持有物字段，故仅靠当前快照无法可靠推回已消耗或被拍落的道具。

## 最小数据与转换

1. 在 `GamePokemon` 增加仅表示本次工厂租借原配的字段，例如 `factoryOriginalHeldItemId: string | null`。生成六只租借和每场敌队时，在同一个确定的 `itemId` 来源处同时设置原配字段与战斗当前字段 `factoryHeldItemId`；`''`/`none` 统一为 `null`。原配字段不进入基地背包，也不因战斗消耗、拍落而变。当前跨世代随机池按槽位分配道具，参考 set 则用 `FactoryReferenceSet.heldItemId`；不能仅存 Frontier set 编号，因为九世代随机池未必有该编号。
2. 战斗效果继续只改 `factoryHeldItemId`。新增独立的下一战准备函数，从不可变的 `factoryOriginalHeldItemId` 重建当前持有物；`null` 恢复为空。它与战后 HP/PP/状态恢复分开，重复调用结果相同。玩家队伍中原配道具已被消耗、被拍落或当前被其他效果替换时，下一战都以该成员的原配为准；不把敌方当前道具或玩家背包道具复制进来。
3. 第 1–6 胜及第 7 胜的结果页恢复 HP、PP 与异常，但持有物保持本场战斗末状态；败退同理且不增加 BP。换怪时新成员来自刚击败的 `enemyTeam`，其原配字段须随它一起进入玩家队伍，其当前持有物仍保持战斗末状态。换怪或跳过后的**下一战开始前**，对确定的三人队伍返还各自原配持有物并落盘；被换出的成员不返还。第七胜没有下一场时不强行返还，若进入下一组，则在新组首战前返还。
4. 处理战果落盘顺序：现有 `resolveBattleResult()` 先调用结算持久化，再执行 `setPlayerTeam(restoreFactoryParty)`。结算可能先把未恢复 HP/PP/异常的队伍写入 `ROUND_RESULT` 检查点；若此刻刷新，内存中的后续恢复不会发生。修改为从本场最终队伍计算恢复后队伍，并在同一个成功的结算/结果提交中写入 `ROUND_RESULT` 快照与恢复后队伍，**保持当前持有物不变**；然后更新 React 状态。结算失败则保持原战斗结果待重试。下一战准备时再把持有物返还与该战启动检查点协调提交，网络失败不得出现界面已开战但存档仍是未返还状态。

## 存档与校验

新 schema 明确要求工厂 READY 快照中的 `factoryRentals`、`playerTeam`、`enemyTeam` 各成员持有合法原配字段（含 `null`）；对实际引用成员检查 ID、原配道具 ID 与当前可变道具的类型。原配道具须在工厂持有物数据中可识别；无原配 `null` 不可被自动补成随机道具。`BATTLE`、`ROUND_RESULT`、`FACTORY_SWAP` 和可续 `BASE` 都允许当前道具已消耗、被拍落；**下一场已启动的 BATTLE 检查点**才应记录返还后的当前道具。交换成员保留自己的原配，不以队伍槽位重新分配。导入含缺失、伪造或不一致字段的同版本 READY 档要触发已有损坏存档保护，不能静默清空快照或猜测来源。

用户允许旧版存档不兼容，因此发布该字段时升级 schema 并沿用旧档明确提示、备份和重新开始路径；不尝试从已被消耗的旧 `factoryHeldItemId` 反推原配。**同一新 schema** 正在进行的战斗快照须保留本场战斗中的已消耗状态，刷新后继续该战；结果、换怪、奖励与基地快照也可继续显示该状态。只有明确进入下一战时才返还。防止旧的 BATTLE 自动保存覆盖更新的战果或下一战检查点，复用现有持久快照新旧阶段保护并补足字段校验。

## 验收

- 单元测试：有原配树果/白色香草的成员战斗中消耗后当前字段为空，赛后 HP/PP/异常恢复仍为空，下一场开战前才恢复同一原配；拍落同理；原配为空仍为空；准备函数连续两次调用完全相同。敌方在战斗中消耗道具后换入玩家队，只在新战前恢复该成员原配；跳过换怪保持原队原配记录；第 7 胜组结算不提前返还。
- 保存测试：战斗中消耗或拍落后刷新，当前战斗道具仍为空且原配字段保留；胜利结算原子落盘后立即刷新，`ROUND_RESULT` 队伍道具仍为空；换怪/跳过、跨组 BASE 续玩、同版导出导入均保留当前状态，下一场起战检查点才返还。模拟结算写盘失败、起战网络失败、双击继续与旧 BATTLE 延迟自动保存，不能提前返还或回滚快照。旧版档有提示，同版本损坏原配字段进入保护页。
- 运行试玩：在模拟手机 390×844 与实体手机分别制造一次可消耗道具、一次拍落、一次敌方道具已消耗后的交换，并覆盖第 3/6 胜奖励节点和第 7 胜组末。逐节点核对战斗日志、持有物显示、快照、刷新及下一战效果；确保战斗中和赛后道具不会提前复活，下一战前只对仍在队伍中的成员返还。保存截图与具体道具、阶段和存档字段证据。
