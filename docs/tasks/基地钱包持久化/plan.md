# 基地钱包持久化实施计划

**已被最新结算与存档规则取代，仅作历史技术记录。** 此计划的逐场胜负入账、旧档余额迁移和旧版导入验收不再执行。当前规则是七战整组获胜后按参考工厂单打表发 BP、败退 0；过往存档无需兼容，可重置或拒绝并明确提示，旧代币不得算作 BP。钱包持久化、原子写入和幂等思路可复用；新实施依据为《docs/公开版规则定稿.md》与 `docs/tasks/组末BP结算/prd.md`。

日期：2026-09-26。产品规则以《docs/公开版规则定稿.md》为准：每场工厂战斗无论胜负，一经结算就立即将该场代币计入基地钱包；玩家回基地即可查看和使用；同一场只入账一次。本任务沿用 `factoryRewards.ts` 的现有奖励计算，不调整数值，也不设定商店价格。

## 当前代码与问题

`useBattleController.ts` 的 `resolveBattleResult` 计算 `getFactoryTokenReward(stage, result)` 后调用 `setCoins(prev => prev + tokens)`；`useFactoryFlow.ts` 的 `startGame` 会 `setCoins(0)`。`usePokeFactoryGame.ts` 初始化余额只读取 `initialBattleResume?.coins ?? 0`，其保存草稿没有独立钱包。`saveManager.ts` 的 schemaVersion 为 7，代币仅在 `factory.battleResume` 快照内；该快照为空或被清理后，局外余额无法恢复。`TopRecordPanel` 和基地首页使用现有 `coins` 展示，可复用这一显示状态。

另一个风险是重复结算：`resolveBattleResult` 当前没有持久结算键。连续触发胜利或失败回调、异步动画重入、刷新后恢复同一战斗，都可能使 `setCoins` 重复执行。仅在内存中禁用按钮不足以覆盖刷新。

## 数据与原子边界

在存档的 `progress` 或独立 `wallet` 下新增长期余额 `balance` 与已经结算的工厂战斗标识集合，并将存档版本升为 8。一个工厂 run 在创建时取得持久 `runId`；每场的结算键由 `runId` 与战次序号组成，胜负结果只是该键的结算内容，不作为可重复获利的不同键。结算记录至少保存键、胜负、实际到账值、结算时间；余额应由已确认的账户状态读取，而不是由战斗快照推导。

将“检查结算键→增加余额→记录结算键”视为一次同步存档更新。调用方拿到“首次结算/已结算”结果后才更新 React 显示和战斗结果。不能让 `setCoins` 更新与记录结算键分散在两个独立的异步保存阶段；否则刷新或后续自动保存可能覆盖其中一半。若保留 `localStorage` 单键存档，应使用一个纯函数产生完整新存档，再一次写入，写入成功才宣告到账；写入失败需留在可重试的结算状态并给玩家可见提示，不能先显示到账再丢失。后续自动保存应基于最新账户版本合并战斗快照，避免旧闭包覆盖新余额和结算记录。

`battleResume.coins` 只作为旧存档迁移输入或兼容字段；新代码以钱包余额为唯一来源。新 run 不清空钱包。调试用 `setCoins(500)` 也应明确仅为 DEV 行为，且通过同一个钱包更新入口处理，不能混入正式结算记录。组结算与返回基地只展示已逐场到账的代币，不再次入账。

## 旧存档迁移

对 schemaVersion ≤7 的存档作一次确定性迁移：若旧存档有 `factory.battleResume.status === 'READY'`，以其中经过非负整数校验的 `coins` 作为初始钱包余额；否则初始余额为 0。旧存档没有可追溯的逐场结算标识，因此不能重建历史交易；不要根据 `highestStreak` 等字段推算补发。迁移后保存 schemaVersion 8，并记录迁移标记，重复加载、导入或刷新不得再次把快照余额叠加。仍在战斗中的旧存档需给当前战次建立稳定的迁移结算键；其旧快照余额视为此前已到账，当前未结算战斗结束时只加该场奖励一次。若旧快照处于已展示结算但未能辨别是否已加币的状态，实施时必须先检查实际快照生成时机并加专项测试，不能盲目补发；无法判定则优先保留旧余额，并由玩家可见说明标出无法恢复的历史数据边界。

导入旧文件也使用同一迁移函数；导出新文件包含钱包与结算键。迁移测试应验证损坏、缺失和非法金额输入不会产生负数、`NaN` 或过大值。余额上限尚未在设计中确定，实施只保留安全整数范围与明确溢出处理，不自行决定游戏经济上限。

## 代码实施顺序

1. `src/services/saveManager.ts`：定义新 schema、迁移和纯结算函数；把余额与结算键纳入规范化、导出和导入。补充 `saveManager.test.ts` 的迁移、幂等、写入失败及重载用例。
2. `src/features/game/hooks/usePokeFactoryGame.ts`：以钱包作为 `coins` 的来源；提供同步结算动作给战斗控制器；创建和保存 `runId`、当前战次；确保现有自动保存不覆盖结算写入。
3. `src/features/game/hooks/useBattleController.ts`：用单一结算动作替换直接 `setCoins`；只有首次结算写入成功才增加可见余额；重复回调继续展示同一结果，不重复到账。
4. `src/features/game/hooks/useFactoryFlow.ts`：新局仅重置局内队伍、道具和进度，保留钱包并生成新 `runId`。检查 DEV 快速开局分支与正式入口边界。
5. `src/features/game/components/game-view/RoundResultScreen.tsx` 与基地显示：核对该场到账、当前余额和返回基地的一致性；若现有 UI 已足够清楚，只改必要反馈。

## 静态与运行验收

静态：`npm run lint`、`npm test`、`npm run build`、`go test ./...`。重点测试胜负各入账一次、同一战次并发或重复回调只入账一次、不同战次分别入账、七战组结算不二次入账、新局不清零、刷新与导出导入保持余额、schema 7 快照迁移只执行一次、空快照不虚构余额、存储写入失败不报成功。测试金额只使用现有 `getFactoryTokenReward` 输出，不固定新的奖励数值。

运行：在当前 Go 服务与前端的手机尺寸页面，从新存档完成胜利和失败各一场，记录战前余额、结果页到账、基地余额、刷新后余额及下一局余额；随后用同一存档重复触发结算路径，观察余额不增加。再用 schema 7 的有快照和无快照样本测试导入与刷新；导出后重新导入应保持金额与结算记录。至少检查 `320×568`、`390×844`、`844×390`，页面文字和按钮可触达、没有横向溢出；记录提交号、数据版本、截图、控制台与服务日志。侧边浏览器尺寸模拟完成后还需实体手机浏览器验收。
