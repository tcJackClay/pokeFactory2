# 基地钱包持久化实施记录

**历史实现记录，尚未满足当前 BP 发放规则。** 下文记录的逐场入账、失败保底和 schema 7 迁移属于旧版本；用户最新要求七战整组获胜后按参考工厂单打表发 BP、败退 0，且不要求兼容过往存档。钱包持久化、原子写入和去重基础可复用；逐场触发、旧币迁移与相应运行证据不能作为新规则验收。旧档重置或拒绝须明确提示，旧代币不得当 BP。

日期：2026-09-26。

## 已实现

- 存档升至 schema 8，`wallet.balance` 是余额唯一来源。开始新局只创建新的 `currentRunId`，保留余额。
- 每场结算使用 `currentRunId + stage` 判重。同一 run 的战次按顺序推进，钱包只存 `settledThrough` 高水位及最后一笔结算，不保存无限增长的结算键集合；组结算不再次入账。
- 每次钱包操作先读取本地存档，构造完整的新存档并同步写入同一 `localStorage` 键。写入成功后才更新界面余额；失败时战斗页保留“重试结算”入口，不显示已到账。
- 结算主存档写入失败时，将原胜负、runId、战次和奖励保存在当前标签页的 `sessionStorage`。同标签刷新后恢复战斗并直接显示重试入口；成功入账后清除待结算记录。终局全队已倒下时不再生成新 `READY` 快照，自动保存沿用最后一个可操作检查点。关闭标签后即使会话记录消失，仍可从该检查点重打。
- 钱包交易递增 `revision`。自动保存遇到较旧的钱包草稿时保留本地较新版本，防止旧 React 闭包回滚结算。奖励重抽和 DEV 调整也走钱包写入。
- 新 run 创建交易同时清空旧 `READY` 快照与挑战暂停字段，避免刷新后旧战斗使用新 runId。结算只接受紧接高水位的下一战；DEV 跳关会创建新 run，并将目标战次之前的战次设为已跳过，余额不增加。
- schema 7 且有有效 `READY` 战斗快照时，将其中经过安全整数校验的 `coins` 迁为钱包余额，并将快照当前战次之前的战次视为已结算。无有效快照迁为 0；不按历史战绩补发。新档再次载入或导入不会重复叠加旧余额。
- 导入存档写入后完整刷新，以恢复导入文件中的战斗和钱包状态；导出包含 schema 8 钱包。

## 仍需运行验收

手机浏览器需分别实测同标签刷新后的直接重试，以及关闭标签再打开后从战前检查点重打；还需检查胜利、失败、导入导出。若浏览器同时拒绝 `localStorage` 和 `sessionStorage` 写入，则无法持久保留已发生的结算结果，界面仍可在未关闭页面时重试。`localStorage` 的读改写是当前标签页内同步操作；多个标签页同时写入同一存档的冲突尚未验证，应在公开版发布门禁前处理或限制并行游玩。
