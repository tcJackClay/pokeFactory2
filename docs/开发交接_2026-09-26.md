## 继续开发的多 Agent 协议

保持用户指定的角色分工：`orchestrator` 持有 PRD/现行规则、拆任务、审技术方案并接受工作；`architect` 查代码和原型，为一个任务写技术及验收计划；`designer` 维护 GDD 和玩家行为；`programmer` 在获准计划上实现并自测；`auditor` 查代码/规则及静态门禁并可修安全局部问题，**不运行游戏**；`player` 运行真实前后端，记录行为和视觉证据，**不写实现代码**；`artist` 处理美术、清单和资源入库；`reviewer` 在当前目标任务全部完成后做最终端到端门禁。并行仅限边界独立的任务，同一战斗控制器避免相互覆盖。Agent 的结论必须附提交号、工作树、命令/结果或运行证据；orchestrator 合并并按结果回填矩阵。下一轮重新派发中断任务，不把中断前的口头通过视为当前代码验收。

建议续接顺序：

1. 核对 `dev`、远端和所有有关工作树；保存未提交轮次事务与 Pivot 内容。先完成轮次 P1，按 architect → programmer → auditor → player → orchestrator 的链验收；不要在其修复前宣称顺风或敌方先手道具通过。
2. 由 designer 将“参考 Rogue 独立商店扩池、四张不同且可领取、无战间回复”写成具体池与卡面规则。由 architect 计划和 programmer 实现七件通用保底、适用的属性强化、道具效果与四卡生成；修正气势头带差异。对任意三件已装备且 TM 候选为零的状态验证仍能生成四卡。
3. 将隔离奖励检查点/UI 与正式池、TM 准入接线，做每组第 3、6 胜先换怪后四卡、刷新固定、领取一次、装备替换和下战返还的模拟手机真实 UI 试玩。TM50 按效果逐项验收再入 allowlist；未验招式不可被随机到。
4. 更新 [需求矩阵](公开版需求矩阵.md)、[规则定稿](公开版规则定稿.md) 和过时的总计划；再逐项完成基地商品与补给券用途等尚未定的设计、代码、试玩。最后由 reviewer 覆盖完整自然七战、跨组、败退、存档、九池、竖横屏、实体手机和生产环境。素材权利路线定稿之前不得宣称可公开发布。
