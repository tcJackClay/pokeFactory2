# PokeFactory2 技术差距与实施顺序

**历史盘点，结算与存档要求已被最新规则取代。** 下表保留 2026-09-26 基线源码的当时差距和原任务拆分，不得作为当前实施依据：用户现已定稿七战整组获胜后按参考工厂单打表发 BP、败退 0、旧版存档无需兼容。旧档可重置或拒绝，但须明确提示且不能把旧代币当 BP。当前实施以《公开版规则定稿.md》和 `docs/tasks/组末BP结算/prd.md` 为准；本表中的“逐场胜负记账”“旧档迁移/升级”“Classic 奖励卡”均已废止。

日期：2026-09-26。基线：`13a7a85` 的源码与《宝可梦对战工厂_项目设计框架_v1.md》《公开版开发与试玩验收总计划.md》。目标是先完成技术与玩法，再准备公开发布手机网页游戏。宝可梦 IP 与素材路线由用户稍后确定。本文是代码核查与实施计划，不代表运行验收。

## 判定依据

设计框架中的“建议”“推荐”仍需先由设计者定稿为可执行规则。已有组件或数据字段只记作代码存在；只有从新存档在当前版本实际操作、记录画面和状态，才能标记为试玩通过。仓库当前没有项目内的 `SKILL.md`，执行流程可按已确定的设计、技术计划、实现、静态审查、试玩、最终验收角色交接；项目的具体产品依据以上两份文档。

## 实施顺序与交接

1. **设计定稿与审计基线**：designer 将设计框架中的建议规则改成明确的玩家行为、数值、解锁和存档要求；player 在当前版本跑完整七战、失败和恢复路径。orchestrator 依据证据更新任务优先级。
2. **局外数据基础**：architect 为钱包、结算、存档迁移写技术与验证方案；programmer 实现；auditor 审查规则与静态检查；player 用真实服务验证持久化。此阶段完成后才能开发商店和培育。
3. **经典工厂闭环**：按首轮试玩的阻断点修复七战、换怪、奖励、组结算、失败和中断恢复；每项有独立静态与运行证据。
4. **基地与长期成长**：商店、培育、图鉴、事件逐项交付；然后接初遇、Rogue、每日、研究和特殊首领。新增资源由 artist 完成素材与索引注册，不能只提交图片。
5. **发布候选**：冻结数据版本，运行 Go 服务与前端生产构建，完成离线上游验证、手机浏览器矩阵、公开入口和回滚演练。IP 与素材路线由用户确定后完成对应的发布清单和资源核查。reviewer 在全部任务完成后独立走端到端质量门，不用静态测试代替试玩。

每个任务的交接记录至少包括：设计依据、源码改动、存档影响、静态检查结果、运行版本及数据版本、存档起点、操作步骤、实际状态、截图、控制台和服务日志、结论。发现失败时回到相应任务，保持“代码存在”“自动检查通过”“运行验收通过”三个状态分离。
