## 产品范围

设计框架是产品需求的基线。对战工厂机制先按[参考索引](../对战工厂_参考索引.md)核对本地参考源码与[原型核对](对战工厂原型核对.md)，再区分参考实现、项目已有规则、用户定稿和新提案。现有代码和旧进度记录只证明曾经实现或检查过某一部分，不能替代当前版本的试玩验收。设计框架中尚未定稿的数值、解锁条件和表现细节，先形成明确规则与玩家可见结果，再进入实现。

首个公开版覆盖以下完整循环：进入基地 → 租借与工厂挑战 → 战斗、换怪及七战整组结算 → 按工厂单打参考表获得并在未来商店消费 Battle Points → 培育与图鉴收集 → 事件和特殊模式 → 返回基地继续长期成长。前六战不发 BP，七战整组胜利后发放，败退 0 BP；第 1、2 组各 3 BP，之后按参考表，击败工厂首领另加 10。经典工厂与 Rogue 工厂、初遇宝可梦、每日挑战、研究任务及特殊首领战均纳入需求核对；若设计框架未给出可执行规则，先补设计，不以页面或按钮存在代替功能完成。当前基地商品未定，先完成钱包与组末结算。

## 工作方式

每项工作使用同一份任务记录，包含：玩家目标、设计依据、完成条件、受影响的存档或数据、实现方案、静态检查、真实试玩步骤、截图或状态证据、已知限制。设计发生变化时，先更新产品规则，再修改代码和验收条件。

一个任务依次经过以下环节：

1. **设计**：从玩家行为定义结果和边界情况；玩法规则写入设计文档。视觉任务先确定可审阅的目标画面。
2. **实现**：只处理该任务的范围，保留可回退的提交。用户不要求兼容过往存档；旧版数据可重置或拒绝导入，但必须明确提示，不能把旧代币当作新 BP。新版本自身的刷新与导入导出仍须可靠。
3. **代码核对**：检查规则对应关系、类型、单元及集成测试、资源引用和构建结果。
4. **试玩验收**：在真实运行的前端与 Go 服务中从玩家入口操作，记录关键状态前后值、控制台和服务日志；画面任务保存实际截图并检查移动端与桌面端。验收失败返回实现环节。
5. **集成验收**：将任务与前后流程连起来试玩，检查存档恢复、失败路径及不同屏幕。只有具备当前提交的运行证据才标记完成。

职责按证据类型区分：设计者负责规则与体验目标，实现者负责代码，代码审查者负责静态正确性，试玩者负责运行状态与画面，最终验收负责跨任务的完整玩家流程。同一人可以承担多个职责，但不能把代码通过当作试玩通过。

## 分阶段交付

| 阶段 | 玩家得到的结果 | 退出条件 |
| --- | --- | --- |
| 0. 当前版本盘点 | 一份可复现的现状报告和需求差距清单 | 新存档完成首次租借、战斗、结算、返回基地；至少覆盖一次失败和一次重开；记录各步画面、状态、接口和错误 |
| 1. 稳定局内闭环 | 经典工厂规则、七战一组、换怪、组末 BP、对手提示、特殊战斗与存档恢复可信 | 前六战不发 BP，第七胜按单打表发放，败退 0；关键规则有测试，完整挑战及中断恢复可在真实服务上复现；移动与桌面操作正常 |
| 2. 基地与经济 | 基地成为清晰的长期入口，先完成持久 BP 钱包，再按定稿商品实现消费、解锁和回访 | 新版本存档数值一致；旧版可重置或拒绝且有明确提示、不把旧代币当 BP；商品定稿后每项消费有来源、价格、效果和反馈 |
| 3. 培育、图鉴与事件 | 培育双槽、蛋队列、图鉴节点、初遇宝可梦、派遣及事件线可持续推进 | 每个来源与奖励可追溯；跨局进度、时间变化和队伍满员等边界可试玩验证 |
| 4. 模式与长期内容 | Classic/Rogue 选择、每日挑战、研究任务和特殊首领战组成长期目标 | 模式规则及奖励互不串档；任务与解锁可完成；重复游玩没有死路或不可恢复状态 |
| 5. 公开发布 | 首次访问者能理解、游玩、保存并恢复；服务可部署和回滚 | 完整数据同步、生产环境端到端试玩、断网/上游故障验证、性能与资源检查、发布回滚演练及最终人工体验验收通过 |

阶段内优先修复阻断玩家流程的问题，再补规则与内容，最后处理单纯外观打磨。每阶段结束时重新试玩从基地到当前阶段终点的整条路径。

## 统一验收记录

每次试玩至少记录：提交号、浏览器及视口、服务与数据版本、存档起点、操作步骤、预期、实际、关键状态前后值、截图位置、控制台与服务错误、结论。状态、画面和操作体验分别下结论；无法观察的项目记为“未验证”。

固定回归路径：新存档开局；6 选 3；出招与换人；胜利和失败；赛后可选换怪；前六战钱包不变与七战胜利按表发 BP；败退 0 BP；返回基地；同版本存档导出导入及战斗中断恢复；旧档重置或拒绝提示；图鉴、事件、商店、培育和两种模式。Rogue 奖励卡规则定稿后再加入对应回归。视觉至少检查 320×568、390×844、844×390、1366×768 四组视口，并在真实可操作状态下检查，不以静态首屏代替。

## 2026-09-26 首轮侧边浏览器试玩

基线提交：`13a7a85`。运行方式：本地 Go 服务 `3001`、Vite `4300`，Codex 侧边浏览器。通过浏览器视口覆盖 `390×844`、`320×568`、`844×390`；这是桌面浏览器的尺寸模拟，还不是实体手机验收。

- `390×844`：从基地开始挑战，六选三，进入战斗，关闭训练家入场台词，选择“电光”并完成一回合。租借与战斗操作可触达；敌方 HP 从 100% 变为 31%，招式 PP 从 20/20 变为 19/20，玩家 HP 从 96/96 降到 64/96，随后受剩饭效果恢复到 70/96。
- `320×568`：战斗状态栏、场地和五个主命令均在视口内；四个招式在回合动画结束后可见并可触达。动画期间命令区曾显示滚动条，需在后续视觉验收中复核稳定状态和滚动体验。
- `844×390`：无明显越界，但战斗场地缩得很小，精灵和状态字难读；列为手机横屏体验问题。
- 本轮浏览器控制台没有 `error` 或 `warn`。战斗日志中出现英文 `restored HP with Leftovers!`，与中文界面混用，列为本地化缺陷。
