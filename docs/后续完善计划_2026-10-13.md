## 产品决策的准备顺序

由 designer 先提交包含来源、玩家流程、具体候选与影响的提案，再询问用户；每次只处理当前阻塞的一组问题。以下是待形成方案的内容，本文不设默认商品或数值。

1. **战斗与 TM 准入**：冲突的持有物消耗规则、TM 效果口径与价格档位；50 项逐项保留状态，任何拟排除项都需说明原因，不以“先做少量”默默删减完整范围。
2. **永久收藏**：已定 Owned 只统计永久获得，租借和换怪只计 Seen。明确初遇伙伴、事件赠予的登记/领取与形态口径；不创建生蛋或孵化系统，原培育提案停止实施。
3. **基地经济与图鉴里程碑**：BP 商品的具体价值、解锁/限购/价格、公平性边界及图鉴/事件是否发 BP。按“组奖励 + 余券”收入给有购物/无购物的可负担例子。旧“情报券/展示位”只是候选，旧价格无效。
4. **长期内容**：开场叙事、初遇伙伴成长与结局分支、保留的非生蛋事件先形成解锁树，再定每日/研究目标的条件/奖励/周期与重放性；每日共同种子、排行榜/分享的首发规则须明确决定。基地展示接入实际获得物。事件钥匙等商品必须随对应效果系统完成，不能只做扣币占位。
5. **交付环境**：目标实体手机及浏览器最低版本、公开地址、仅本机存档或其他方案、备份/回滚责任。素材使用依据单独跟踪，不影响已授权的技术与玩法完善。

## 多 Agent 执行与验收约束

- orchestrator 负责 PRD、任务路由、方案评审、验收和矩阵；详细技术方案与验证设计交给 architect。designer 维护玩法规则，artist 只按已定需求登记素材。
- 每个实现任务仍走 `prd.md → plan.md/context.json → programmer → auditor → player → orchestrator`。architect 的实质性打回 0–2 次走 Route A，超过 2 次走 Route B。任务 `log.md` 只追加。
- `useBattleController.ts` 同时只能由一个任务修改；`saveManager.ts` 的结构/版本/交易更改串行。TM 学习、基地购买和事件写入不能同时改同一存档核心。
- auditor 不运行游戏，player 不改实现。浏览器运行时冻结代码，同时运行 Vite 与 Go，记录源码 SHA、运行根目录、视口、初始存档、实际 UI 操作、状态和截图。受控注入、自然操作、DEV Win、实体手机及生产证据分别记录。
- 修代码后重取受影响证据；全程不把历史截图、模拟视口或静态绿灯当最终公开版验收。旧四卡分支禁止直接合并。
- 每任务完成后更新矩阵中的实现状态、证据等级与剩余缺口。最终 reviewer 只在完整公开版范围完成后启动最终检查；本轮计划阶段不创建新 reviewer，不释放既有 review lock。
